README — вход за пять минут. Здесь то, что нужно, когда уже запустил и хочешь
разобраться: все эндпоинты с кодами ошибок, поведение витрины, платёжная

Решения с альтернативами — [DECISIONS.md](DECISIONS.md), схема —

## Демо-данные: параметры seed

```bash
make seed    # docker compose exec backend python -m app.scripts.seed
```

По умолчанию: распродажа на 5 единиц, старт через 2 минуты, длительность
30 минут, по одной распродаже у каждого из двух магазинов.

| Аргумент | Единицы | По умолчанию | Что принимает |
|---|---|---|---|
| `--quantity` | штуки | 5 | не меньше 1 |
| `--start-in` | **минуты** | 2 | `0` — стартует сейчас; отрицательное — уже идёт |
| `--duration` | **минуты** | 30 | не меньше 1; `0` отклоняется с сообщением, потому что `CHECK ck_sales_period_valid` требует `end_at > start_at` |

```bash
# распродажа уже идёт прямо сейчас
docker compose exec backend python -m app.scripts.seed --start-in 0 --duration 30

# стартует через минуту: видно таймер и как включается кнопка «Купить»
docker compose exec backend python -m app.scripts.seed --start-in 1 --duration 10

# одна единица — чтобы увидеть гонку двух покупателей
docker compose exec backend python -m app.scripts.seed --start-in 0 --duration 90 --quantity 1

# короткая распродажа: через минуту сама закроется, видно статус «Завершена»
docker compose exec backend python -m app.scripts.seed --start-in 0 --duration 1
```

**Повторный запуск безопасен.** Пользователи и товар переиспользуются.
Распродажа **своего seed-товара** обновляется под новые параметры, если по ней
ещё нет броней; если брони есть, трогать её нельзя — создаётся новая, поэтому
после нескольких прогонов с покупками распродаж становится больше. Чужие
распродажи seed не трогает никогда. Полный сброс — `docker compose down -v`.

## API

Живая документация — Swagger на http://localhost:8000/docs.

Вход без пароля (ADR-007): `POST /api/auth/login` с email отдаёт JWT, неизвестный
email становится покупателем. Токен передаётся как `Authorization: Bearer <token>`.

### Резерв

`POST /api/sales/{id}/reservations` — нужен токен. Занимает одну единицу товара
и создаёт бронь в статусе `held` на `RESERVATION_TTL_SECONDS` (по умолчанию 10 минут).

Единица занимается одним атомарным условным `UPDATE` в БД (ADR-002): остаток
не вычитывается в приложение и не проверяется в Python, поэтому последнюю единицу
нельзя выдать двоим даже при одновременных запросах.

### Формат ошибок резерва

Четыре разные ситуации отдают один и тот же `409`, поэтому в теле ошибки есть
**машинный код** — ветвиться по тексту сообщения нельзя:

```json
{
  "detail": {
    "code": "sold_out",
    "message": "Товар разобрали"
  }
}
```

| HTTP | `code` | Когда |
|---|---|---|
| 401 | — | токена нет или он недействителен |
| 404 | `sale_not_found` | распродажи с таким id нет |
| 409 | `not_started` | распродажа ещё не началась |
| 409 | `ended` | окно истекло или распродажу закрыли досрочно |
| 409 | `sold_out` | товар разобрали |
| 409 | `already_reserved` | у покупателя уже есть активная бронь на эту распродажу |

Почему `409`: это конфликт с текущим состоянием ресурса. `425 Too Early`
предназначен для TLS early-data, а `410 Gone` говорит о безвозвратно удалённом
ресурсе — распродажа же существует и читается.

Любой отказ откатывает транзакцию целиком: счётчик `held` не остаётся
увеличенным без соответствующей брони.

### Отмена брони

`DELETE /api/reservations/{id}` — нужен токен. Переводит **свою** бронь из `held`
в `cancelled` и возвращает единицу товара. Успех — **204 No Content**, без тела.

Операция **идемпотентна**: повторная отмена и уже завершённая бронь тоже дают 204,
поэтому повторный клик или ретрай ничего не ломают. Отмена — такой же условный
`UPDATE ... WHERE status = 'held' RETURNING`, как и резерв: десять одновременных
отмен уменьшают `held` ровно на один.

| HTTP | `code` | Когда |
|---|---|---|
| 204 | — | бронь отменена; либо уже была `cancelled`, `expired` или `failed` — единица давно вернулась |
| 401 | — | токена нет или он недействителен |
| 404 | `reservation_not_found` | брони нет **или она принадлежит другому покупателю** |
| 409 | `not_cancellable` | бронь в `paying` или `paid` — начатая оплата доводится до конца (инвариант 4) |

Чужая бронь отвечает тем же 404, что и несуществующая: иначе по коду ответа можно
было бы перебором выяснить, какие брони существуют.

### Оплата

`POST /api/reservations/{id}/pay` — нужен токен, только своя бронь. Переводит
бронь `held → paying`, создаёт заказ (сумма фиксируется по цене распродажи)
и платёж, затем обращается к платёжной системе.

**Вызов провайдера идёт после коммита, вне транзакции** (ADR-022): сетевой
запрос не держит блокировки БД. Это возможно потому, что бронь в `paying`
не истекает (инвариант 4) — свипер её не трогает, сколько бы ни ждал провайдер.

Ключ идемпотентности выводится из брони (`pay:<reservation_id>`), поэтому
повторный «Оплатить» и повтор после сетевого сбоя приходят к заглушке с тем же
ключом — она возвращает тот же платёж, а не создаёт второй.

| HTTP | `code` | Когда |
|---|---|---|
| 200 | — | заказ создан (или уже был — `already_started: true`), провайдер принял платёж |
| 202 | — | заказ создан, но провайдер не ответил: `provider_state: awaiting_provider` |
| 401 | — | токена нет или он недействителен |
| 404 | `reservation_not_found` | брони нет или она принадлежит другому покупателю |
| 409 | `reservation_expired` | бронь истекла |
| 409 | `reservation_cancelled` | бронь отменена |
| 409 | `payment_failed` | предыдущая оплата была отклонена |
| 409 | `sale_ended` | распродажа завершена — новую оплату начать нельзя |

Недоступность платёжной системы — **не 500**: наша часть работы выполнена
и зафиксирована, заказ остаётся `pending_payment` и ждёт сверки.

### Результат платежа

`POST /api/payments/webhook` принимает результат от заглушки. Подпись
проверяется по **сырому телу** (`X-Signature: sha256=<hex>`), неверная → **401**,
и тело даже не разбирается.

Платёж ищется по **нашему** `idempotency_key`, а не по id заглушки: если ответ
на создание платежа не дошёл, `provider_payment_id` у нас пустой — он
дозаписывается из вебхука.

| результат | что меняется |
|---|---|
| `succeeded` | платёж `succeeded`, заказ `paid` + `paid_at`, бронь `paid`, `held - 1` и `sold + 1`, письмо в `outbox` |
| `declined` | платёж `declined`, заказ `failed`, бронь `failed`, `held - 1` — единица возвращается на витрину |

Повторный вебхук получает **200** и ничего не меняет: решение принимает условный
`UPDATE payments WHERE status = 'pending'`, поэтому `sold + 1` происходит один
раз, а письмо не дублируется (`dedup_key` + `ON CONFLICT DO NOTHING`).
200 нужен, чтобы заглушка перестала повторять уже применённый результат.

Письмо кладётся в `outbox` в той же транзакции, а отправляет его фоновый
цикл — см. [«Письма»](#письма).

### Закрытие распродажи

Когда `end_at` прошёл, фоновый воркер закрывает распродажу: заполняет
`closed_at`, снимает неоплаченные брони в `held` и кладёт их владельцам письмо
«Распродажа завершена». Интервал — `SALE_CLOSER_INTERVAL_SECONDS` (5 с),
первый проход сразу при старте, поэтому распродажи, закончившиеся за время
простоя сервера, закрываются при запуске.

**Что значит «непроданное снимается с продажи».** Закрытие трогает только
счётчик `held` и `closed_at`. **`quantity` не уменьшается** — магазину нужна
цифра «сколько не продано», и она считается как `quantity - sold`. Купить нельзя
не потому, что товара нет, а потому что распродажа закрыта: статус становится
`ended`, резерв и оплата отказывают.

**Брони в `paying` не снимаются** (инвариант 4): начатая оплата доводится
до конца, и успешный результат после закрытия по-прежнему делает заказ `paid`.
Поэтому письмо «корзина очищена» уходит только владельцам `held` — у кого
оплата идёт, те получат письмо об оплате при успехе.

Начать **новую** оплату после `end_at` нельзя, даже если воркер ещё не прошёл:
`POST /api/reservations/{id}/pay` отдаёт **409** с кодом `sale_ended`.

Витрина узнаёт о закрытии сама: триггер в БД следит и за `closed_at`, поэтому
по WebSocket приходит снимок со статусом `ended` (ADR-020, ADR-025).

`SALE_CLOSER_ENABLED=false` выключает воркер (в лог уйдёт WARNING: закончившиеся
распродажи останутся открытыми).

### Письма

Письмо об оплате пишется в таблицу `outbox` **в той же транзакции**, что и смена
статуса заказа (ADR-004), а отдельный фоновый цикл отправляет его в SMTP.
Письма видны в Mailpit: http://localhost:8025

**Граница гарантии — честно.** Запись в `outbox` строго одна на событие:
уникальный `dedup_key`, поэтому повторный вебхук и сверка второй строки
не создают. Доставка же — **at-least-once**: между «SMTP принял письмо»
и «отметили отправленным» нет общей транзакции, и падение процесса ровно
в этом окне даёт либо потерю, либо дубль.

Выбран **дубль**: потерянное письмо об оплате означает, что покупатель заплатил
и не узнал об этом, а второе такое же письмо безвредно. У письма постоянный
`Message-ID`, выведенный из `dedup_key`, поэтому повтор опознаётся
и подавляется на стороне получателя.

Ошибка SMTP — повтор с нарастающей паузой (`OUTBOX_RETRY_BASE_SECONDS * 2^попытки`),
после `OUTBOX_MAX_ATTEMPTS` письмо помечается `failed`, причина остаётся
в поле `last_error`. Строка, занятая упавшим процессом, возвращается в работу
по истечении аренды `OUTBOX_LEASE_SECONDS`.

`SMTP_TIMEOUT_SECONDS` обязан быть не больше половины `OUTBOX_LEASE_SECONDS` —
иначе приложение не стартует. Без этого медленный SMTP давал бы дубль
в штатной работе: аренда истекла бы, пока первый отправитель ещё ждёт ответа.

`OUTBOX_ENABLED=false` выключает отправку (в лог уйдёт WARNING: письма
останутся в таблице).

### Если вебхук потерялся

Вебхук — нормальный путь, но он может не дойти: у заглушки повторы не
бесконечны, да и ответ на создание платежа мог потеряться. Поэтому backend сам
доспрашивает провайдера о платежах без результата (ADR-023).

**Заказ досчитывается не позже чем через `RECONCILE_BACKOFF_MAX_SECONDS`**
(по умолчанию 300 с) — это потолок интервала между проверками одного платежа.
Обычно гораздо быстрее: первый проход идёт через `RECONCILE_GRACE_SECONDS`
после создания платежа, дальше интервал растёт как
`RECONCILE_BACKOFF_BASE_SECONDS * 2^попытки` до потолка.

Переспрос делается **тем же** `POST /payments` с тем же `idempotency_key`:
известный платёж вернётся с текущим статусом, а неизвестный — если создание
не дошло — будет создан сейчас. Одна операция закрывает оба случая.

Платёж в режиме `hang` остаётся `pending` сколько угодно: заказ не отменяется,
потому что начатая оплата доводится до конца (инвариант 4). Как только платёж
отпустят на страничке заглушки, сверка это увидит и завершит заказ.

Недоступность провайдера во время сверки ничего не ломает: платёж останется
`pending` и будет проверен позже.

`RECONCILER_ENABLED=false` выключает сверку (в лог уйдёт WARNING: платежи
без вебхука останутся в `pending`). Интервалы `<= 0` — ошибка конфигурации,
приложение не стартует.

### Когда бронь возвращается на витрину

Бронь в `held` живёт `RESERVATION_TTL_SECONDS` (по умолчанию 600 с). Истёкшие
брони снимает фоновый свипер, который просыпается каждые `SWEEPER_INTERVAL_SECONDS`
(по умолчанию 2 с) — первый проход сразу при старте backend.

**Единица возвращается на витрину не позже чем через `RESERVATION_TTL_SECONDS` +
`SWEEPER_INTERVAL_SECONDS`** — по умолчанию 10 минут 2 секунды. Именно «не позже»,
а не «ровно»: свипер просыпается по интервалу, а не по таймеру каждой брони,
поэтому бронь, истёкшая сразу после прохода, подождёт до следующего.

Свипер выбирает работу запросом к БД, а не из таймеров в памяти (ADR-010):
перезапуск backend ничего не теряет, просроченное обработается при старте.
Брони в `paying` он не трогает — начатая оплата доводится до конца.

`SWEEPER_ENABLED=false` выключает свипер (в лог уйдёт WARNING: занятые единицы
останутся занятыми). Нулевой или отрицательный `SWEEPER_INTERVAL_SECONDS` — ошибка
конфигурации, приложение не стартует: случайный ноль не должен молча останавливать
возврат броней.

### Live-обновления остатка

`WS /ws/sales/{id}` — вход не нужен, смотреть витрину может любой. Сразу при
подключении приходит снимок, дальше — после каждого изменения:

```json
{
  "sale_id": "...",
  "quantity": 5,
  "sold": 0,
  "held": 1,
  "remaining": 4,
  "status": "active",
  "server_time": "2026-10-10T17:52:03.118Z"
}
```

Сигнал отправляет триггер в БД — внутри той же транзакции, что меняет счётчики
(ADR-020). Поэтому уведомление приходит **только при коммите**: отказ резерва
(`sold_out`, `already_reserved`) обновления не даёт. Триггер вместо вызова
из кода выбран по одному критерию: новая операция не должна иметь шанса забыть
уведомление.

В сигнале только id распродажи — состояние перечитывается из БД, чтобы остаток
не «прыгал назад» при обгоне сообщений. Пачка изменений за `LIVE_UPDATE_WINDOW_MS`
(по умолчанию 50 мс) склеивается в один запрос и одну рассылку.

Если распродажи нет, соединение закрывается с кодом **4404**.

Слушатель живёт на отдельном соединении вне пула; при разрыве он переподключается
и досылает свежие снимки всем подписчикам — сигналы за время разрыва потеряны.

### Подписка на несколько распродаж сразу

`WS /ws/sales?ids=<id>,<id>,...` — одно соединение на все распродажи дашборда.
По соединению на каждую было бы расточительно: десять распродаж — десять TCP-соединений
и десять задач на один экран (ADR-026).

Кадры различаются полем `type`, а не формой, чтобы клиент не угадывал по структуре:

```json
{"type": "snapshot", "sales": [{"sale_id": "...", "sold": 0, "held": 1, "...": "..."}]}
{"type": "update", "sale": {"sale_id": "...", "sold": 1, "held": 0, "...": "..."}}
```

Снимок приходит при подключении — по нему экран отрисовывается целиком. Дальше
`update` на каждое изменение, по одной распродаже за кадр.

- предел — **100 уникальных** id на соединение, иначе закрытие с кодом **4413**.
  Дубли просто сворачиваются: они не создают нагрузки;
- неизвестные id и мусор соединение не ломают — их просто нет в снимке.
  Распродажу могли удалить, и дашборд из-за этого слепнуть не должен.

Старый `WS /ws/sales/{id}` остался — им пользуется страница распродажи.

### Свои брони

`GET /api/reservations/me` — брони покупателя в `held` и `paying`. `server_time`
одно на весь ответ: по смещению от него клиент считает, сколько осталось у каждой
брони, не доверяя часам браузера (ADR-009).

```json
{
  "server_time": "2026-10-10T14:25:32.747888Z",
  "reservations": [
    {
      "id": "...",
      "sale_id": "...",
      "status": "held",
      "expires_at": "2026-10-10T14:35:24.406659Z"
    }
  ]
}
```

Остальные эндпоинты отдают `detail` простой строкой — машинный код нужен только
там, где у одного HTTP-кода несколько разных причин.

### Дашборд магазина

`GET /api/shop/sales` — только роль `shop`. Покупатель получает **403**, гость — **401**.
Видны только распродажи своих товаров: фильтр по `products.shop_id`, а не по списку id
из запроса.

```json
{
  "server_time": "2026-10-12T02:31:07.412Z",
  "sales": [
    {
      "id": "...",
      "product_id": "...",
      "product_name": "Беспроводные наушники Flash One",
      "price_minor": 499000,
      "currency": "KGS",
      "quantity": 5,
      "sold": 2,
      "held": 1,
      "remaining": 2,
      "status": "active",
      "start_at": "...",
      "end_at": "...",
      "closed_at": null,
      "unsold": null,
      "revenue_minor": 998000,
      "paid_orders_count": 2
    }
  ]
}
```

- **Выручка — только заказы `paid`.** `pending_payment` и `failed` не считаются:
  деньги получены только по оплаченным. Фильтр в SQL, не в Python.
- **`unsold` заполняется только после закрытия.** Пока распродажа идёт, «не продано»
  не имеет смысла — остаток ещё может уйти. После закрытия это `quantity - sold`
  (`quantity` при закрытии не меняется как раз ради этой цифры).
- **Один запрос на весь экран.** Агрегаты считаются `LEFT JOIN LATERAL` рядом
  со строкой распродажи. Есть тест, который считает запросы к `sales` и требует
  ровно один: N+1 поймается сразу, если кто-то соберёт выручку в цикле.
  Частичный индекс `orders (sale_id) WHERE status = 'paid'` — чтобы подсчёт
  не просматривал всю таблицу заказов.

На странице `/shop` счётчики приходят по WS одним соединением, а выручка
перезапрашивается по HTTP, когда в снимке изменился `sold` (в снимке выручки нет).
Серия продаж склеивается в один запрос за 300 мс; изменения `held` выручку
не трогают, поэтому по ним запроса нет. Изменившаяся ячейка на секунду подсвечивается.

Ссылка «Магазин» в шапке видна только роли `shop`. Покупатель, открывший `/shop`
по прямой ссылке, видит понятное «раздел доступен только магазинам» со ссылками
на витрину и свои заказы, а не пустой экран.

## Витрина

Фронт и бэк общаются по сети, адрес API берётся только из `VITE_API_URL` (ADR-015).
Все запросы и WebSocket идут через единственный модуль `frontend/src/api` — вызовов
`fetch` и `WebSocket` в остальном коде нет.

**Живой остаток.** Страница распродажи подписана на `WS /ws/sales/{id}`: остаток
и статус меняются без перезагрузки, рядом индикатор «на связи / переподключение».
При обрыве фронт переподключается с нарастающей паузой (0.5 → 1 → 2 → 4 → 8 → 10 с);
догонять состояние не нужно — сервер присылает снимок сразу при подключении.

**Таймеры по серверному времени.** При загрузке один `GET /api/time`, дальше тик
локальный по измеренному смещению. Кнопка «Купить» никогда не включается по часам
браузера: когда отсчёт до старта доходит до нуля, состояние перезапрашивается
у сервера.

**Корзина** восстанавливается из `GET /api/reservations/me`, поэтому переживает
обновление страницы. В ней отсчёт до `expires_at`, кнопка «Отменить»
и кнопка «Оплатить» — про её состояния ниже.

**Оплата.** Кнопка «Оплатить» в корзине вызывает `POST /api/reservations/{id}/pay`
и блокируется, пока запрос идёт. Дальше корзина показывает состояние:
«ждём подтверждения оплаты» при `accepted` либо «платёжная система недоступна,
повторим автоматически» при `awaiting_provider`. Отсчёт брони и кнопка отмены
при этом скрываются: бронь в `paying` не истекает, и тикающий к нулю таймер
пугал бы зря.

**Итог оплаты без перезагрузки.** Успешная и отклонённая оплата меняют счётчики
распродажи, поэтому по WebSocket приходит снимок — по нему вкладка
перезапрашивает свои заказы и корзину. Сокет публичный и про чужие заказы
ничего не знает, поэтому он служит сигналом «что-то изменилось», а не источником
результата. Подстраховка — редкий опрос раз в 10 секунд, и только пока есть
заказ в ожидании: на витрине без незавершённых заказов запросов нет вовсе.

**Закрытие распродажи.** Если у вкладки была корзина в `held`, а пришёл статус
`ended` и брони больше нет, показывается «Распродажа завершена, корзина
очищена».

**Вкладки одного покупателя** синхронизируются через `BroadcastChannel` — браузерный
API, **ноль дополнительных запросов к бэкенду**. Публичный WebSocket сообщает только
об изменении остатка и не знает, чья бронь, а опрашивать `/me` на каждое обновление
означало бы нагрузку «обновления × вкладки». Страховка — перезапрос при возврате
на вкладку.

**Истечение брони.** Ноль на отсчёте фронт истечением не считает: единицу возвращает
свипер, и подтвердить это может только ответ сервера. Пока сервер не подтвердил,
состояние перезапрашивается раз в секунду, но не дольше 30 секунд — дальше
показывается «не удалось обновить корзину, обновите страницу».

## Платёжная заглушка

Отдельный сервис `payment-stub` изображает платёжного провайдера. Он не
переиспользует код и БД основного сервиса — у него своё хранилище SQLite
в отдельном volume (ADR-021): иначе не проверялись бы сетевые сбои,
асинхронный ответ вебхуком и независимый перезапуск «чужой» системы.

**Страничка управления: http://localhost:8100** — текущий режим с переключателем,
список платежей и кнопки «одобрить / отклонить» у зависших. Обновляется сама
раз в две секунды.

### Режимы

| Режим | Что делает |
|---|---|
| `approve` | через заданную задержку платёж становится `succeeded` |
| `decline` | через заданную задержку платёж становится `declined` |
| `hang` | платёж навсегда остаётся `pending` — отпускается только вручную |

Режим по умолчанию задаётся в `.env` (`PAYMENT_MODE`, `PAYMENT_DELAY_MS`),
переключается на лету на страничке или запросом:

```bash
curl -X POST localhost:8100/control/mode -H 'Content-Type: application/json' \
  -d '{"mode":"hang"}'

# задержка ответа и дублирование вебхуков
curl -X POST localhost:8100/control/mode -H 'Content-Type: application/json' \
  -d '{"mode":"approve","delay_ms":3000,"duplicate_webhooks":true}'
```

Режим запоминается в хранилище заглушки, поэтому переключение не теряется
при перезапуске. У каждого платежа остаётся **тот режим, с которым он создан**:
смена режима на лету не меняет судьбу уже начатых платежей.

`duplicate_webhooks` присылает результат дважды — так проверяется идемпотентность
приёма на стороне backend.

### Как отпустить зависший платёж

На страничке у платежа в статусе «ждёт» есть кнопки **одобрить** и **отклонить**.
То же запросом:

```bash
curl -X POST localhost:8100/payments/<payment_id>/resolve \
  -H 'Content-Type: application/json' -d '{"result":"approve"}'
```

Повторное решение по тому же платежу даёт `409 already_resolved` — первое
не перебивается.

### Что ещё стоит знать

- `POST /payments` идемпотентен по `idempotency_key`: первый вызов — **202**,
  повторный с тем же ключом — **200** и тот же платёж, тот же ключ с другой
  суммой — **409** `amount_mismatch`.
- Вебхук подписан: `X-Signature: sha256=<hex HMAC-SHA256 тела>`, секрет общий
  через `PAYMENT_WEBHOOK_SECRET`.
- **Вебхук может потеряться.** Повторы идут с нарастающей паузой (5 попыток),
  после чего заглушка сдаётся — ровно как настоящий провайдер. Статус при этом
  остаётся доступен через `GET /payments/{id}`, и потерю закрывает сверка
  на стороне backend.
- Перезапуск во время задержки не оставляет платёж висеть: срок хранится в БД,
  и при старте просроченные доделываются. Платежи в режиме `hang` не трогаются.
- Внутри docker-сети backend обращается к заглушке по `http://payment-stub:8000`,
  а заглушка стучится обратно на `http://backend:8000`.

## Если порт занят

Нужны свободные **8000** (API) и **5173** (витрина), а также **1025** и **8025** (Mailpit).
Порт Postgres на хост не публикуется, поэтому локальный Postgres на 5432 запуску
не мешает (ADR-017).

Признак занятого порта в выводе `make up`:

```
Error ... failed to bind host port for 0.0.0.0:8000 ... address already in use
```

Кто держит порт:

```bash
lsof -nP -iTCP:8000 -sTCP:LISTEN     # macOS / Linux
```

Порты задаются в `.env` — поправьте и повторите `make up`:

```ini
BACKEND_PORT=8001
FRONTEND_PORT=5174
MAILPIT_SMTP_PORT=1026
MAILPIT_UI_PORT=8026
```

Меняя `BACKEND_PORT`, поправьте и две связанные переменные, иначе браузер будет
стучаться не туда, а бэкенд отклонит запрос по CORS:

```ini
VITE_API_URL=http://localhost:8001
CORS_ORIGINS=http://localhost:5174
```

### Доступ к базе внешним клиентом

По умолчанию порт Postgres не опубликован. Проще всего зайти изнутри:

```bash
docker compose exec postgres psql -U flash_sale -d flash_sale
```

Если нужен psql или GUI-клиент с хоста, включите публикацию порта:

```bash
cp docker-compose.override.example.yml docker-compose.override.yml
make up
```

`docker compose` подхватывает `docker-compose.override.yml` сам, без дополнительных
флагов. Файл в git не попадает. Порт берётся из `POSTGRES_PORT` в `.env` (по умолчанию 5433).

## Тесты и линт

```bash
make test    # тесты backend и платёжной заглушки
make lint    # ruff + oxlint + tsc, см. ниже
make load    # нагрузочный прогон: 200 покупателей на 10 единиц
```

Всё это же гоняется в CI на каждый PR и пуш в `main`
([.github/workflows/ci.yml](../.github/workflows/ci.yml)), тремя параллельными job:

| Job | Что делает |
|---|---|
| backend | тесты на **реальном Postgres 16** сервисом, ruff (линт и формат) |
| payment-stub | свои тесты заглушки, ruff — Postgres ей не нужен (ADR-021) |
| frontend | oxlint, `tsc --noEmit`, сборка |

Job бэкенда идёт внутри того же образа, что и dev-контейнер, поэтому сервисы
доступны по именам `postgres` и `mailpit` — как в `docker compose`, и тесты
не приходится править под CI.

**Mailpit в CI поднимается сервисом, а не пропускается.** Тест
`test_letter_reaches_real_mailpit` отправляет письмо настоящим SMTP и читает
его обратно через API Mailpit — пропустить его означало бы потерять ровно ту
проверку, ради которой он написан, и оставить в зелёном CI только фейковый
отправитель. Пропуск остался на случай действительно недоступного сервиса,
с явной причиной в выводе.

`make lint` выполняет четыре команды:

```bash
docker compose exec backend ruff check .
docker compose exec backend ruff format --check .
docker compose exec payment-stub ruff check .
docker compose exec payment-stub ruff format --check .
docker compose exec frontend npm run lint        # oxlint
docker compose exec frontend npm run typecheck   # tsc
```

У заглушки свой прогон тестов — она изолирована от основного сервиса (ADR-021):

```bash
docker compose exec payment-stub pytest -q
```

Линтер фронтенда — **oxlint** (конфиг `frontend/.oxlintrc.json`), он идёт
в современном шаблоне Vite вместо ESLint. ESLint в проекте не используется.

Тесты бэкенда идут на **реальном Postgres**, в отдельной базе `flash_sale_test`:
она пересоздаётся перед каждым прогоном, схема накатывается миграциями, после прогона
база удаляется. Рабочая база не затрагивается — имя тестовой обязано заканчиваться
на `_test` и отличаться от базы из `DATABASE_URL`, иначе тесты падают, не выполнив
ни одного запроса (ADR-011).

Логи: `make logs` (`docker compose logs -f`), одного сервиса — `docker compose logs -f backend`.

## Структура

```
backend/     FastAPI: api/routes + api/schemas → services → models, миграции Alembic
frontend/    Vite + React + TypeScript; все запросы через единственный модуль src/api
payment-stub/  эмулятор платёжки: свой сервис, своё хранилище SQLite
docs/        решения (ADR), модель данных, журнал разработки, лог промптов
.github/workflows/   CI: тесты, линт, типы, сборка на каждый PR
docker-compose.yml   postgres, mailpit, backend, frontend
Makefile     короткие обёртки над docker compose
.env.example шаблон окружения, копируется в .env
```

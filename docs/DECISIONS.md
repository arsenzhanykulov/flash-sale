## ADR-001. Стек: FastAPI + PostgreSQL + React
**Дата:** <!-- Thu Oct  8 23:59:31 +06 2026 -->
**Контекст:** нужен отдельный backend и frontend, реляционная БД, WebSocket для live-обновлений.
**Решение:** FastAPI (async, WebSocket из коробки, Swagger как живая документация API),
SQLAlchemy 2 async + asyncpg, Alembic, PostgreSQL 16; React + Vite + TypeScript.
**Альтернативы:** Django (тяжелее, async слабее), Node.js/NestJS (меньше моего опыта).
**Последствия:** весь бэк асинхронный; для критичных операций пишем явный SQL.

## ADR-002. Резерв — атомарный условный UPDATE
**Контекст:** последнюю единицу нельзя продать двоим.
**Решение:** счётчики `sold`/`held` в `sales` и один `UPDATE ... WHERE sold + held < quantity RETURNING`.
Плюс CHECK-ограничение `sold + held <= quantity` как страховка.
**Альтернативы:** `SELECT ... FOR UPDATE` (корректно, но держит блокировку дольше и
сериализует всех на чтении); Redis-счётчик (ещё один источник правды, сложнее восстановление);
SERIALIZABLE (ретраи на каждом конфликте).

**Альтернатива «очередь» (asyncio.Lock / Redis / RabbitMQ) — почему не выбрали:**
- `asyncio.Lock` живёт в одном процессе. Два воркера uvicorn или два инстанса — и защиты
  нет; состояние блокировки умирает вместе с процессом. Это не защита, а её видимость.
- Redis-блокировка — ещё один источник правды и ещё один сервис. Срок жизни блокировки
  не связан с длительностью транзакции: если транзакция затянулась, блокировка истечёт
  и второй запрос войдёт в критическую секцию. Чтобы это закрыть, нужны fencing-токены
  и проверка владения — больше кода, чем сам резерв.
- Очередь команд резерва (RabbitMQ и подобное) даёт честный порядок обслуживания,
  но делает запрос асинхронным: клиенту нужен поллинг или push, чтобы узнать результат.
  Плюс брокер в инфраструктуре, плюс пропускная способность упирается в одного
  консьюмера, а `CHECK` в БД всё равно остаётся нужен как последняя линия защиты.
- Главное: Postgres **уже** сериализует условный `UPDATE` на блокировке строки.
  Очередь дублировала бы то, что БД делает бесплатно и переживая перезапуск.
- Очередь была бы оправдана, если бы требовался гарантированный порядок
  «кто первым нажал» или решение зависело от внешних систем. Здесь достаточно
  блокировки одной строки.

**Последствия:** счётчики должны меняться только вместе со статусом брони в одной транзакции;
есть тест на согласованность `held` = число броней в `held/paying`.
Важная деталь, выясненная на шаге 2.1: `CHECK (sold + held <= quantity)` спасает **только**
если запись — инкремент (`held = held + 1`). Наивная версия писала посчитанное в Python
абсолютное значение, и `CHECK` молчал: оба запроса писали `held = 1`, `0 + 1 <= 1` проходило
дважды. При инкременте та же гонка упирается в `ck_sales_not_oversold` — проверено
намеренной поломкой условия в `UPDATE`.

## ADR-003. Live-обновления: WebSocket + Postgres LISTEN/NOTIFY
**Решение:** после коммита изменения остатков бэк делает `NOTIFY`, слушатель рассылает событие
всем WebSocket-клиентам распродажи.
**Альтернативы:** in-memory pub/sub (не работает с несколькими инстансами), Redis pub/sub
(лишний сервис), polling (задержка и нагрузка).
**Последствия:** клиент после переподключения запрашивает актуальное состояние по HTTP.

## ADR-004. Ровно одно письмо: transactional outbox
**Решение:** письмо пишется в `outbox` с уникальным `dedup_key` в той же транзакции,
что и смена статуса; отдельный цикл отправляет pending в SMTP.
**Альтернативы:** отправка прямо из обработчика (письмо может уйти при откате транзакции
или уйти дважды при повторе вебхука).
**Последствия:** гарантия «не более одного письма на событие»; при падении SMTP — ретраи.

## ADR-005. Платёжная заглушка — отдельный сервис
**Решение:** `payment-stub` на FastAPI: режимы approve / decline / hang, задержка,
ответ вебхуком + эндпоинт статуса. Бэк при зависании периодически сверяет статус сам.
**Альтернативы:** заглушка внутри бэка (не проверяет сетевые сбои и асинхронность ответа).

## ADR-006. Почта: Mailpit
**Решение:** настоящий SMTP в Mailpit, письма видны в веб-UI — «ровно одно письмо» проверяется глазами и тестом через API Mailpit.

## ADR-007. Упрощённый вход
**Решение:** вход по email без пароля → подписанный токен (JWT). Роли `buyer` / `shop`.
**Почему:** задание разрешает; фокус на конкурентности, а не на аутентификации.
**Следующий шаг:** magic link по почте или пароль.

## ADR-008. Одна бронь = одна единица, одна единица на покупателя
**Решение:** частичный уникальный индекс `(sale_id, user_id)` по активным статусам.
**Почему:** при дефиците товара честнее распределять по одной; упрощает модель.
**Альтернатива:** N единиц на покупателя — поле `qty` в брони и лимит в UPDATE.

## ADR-009. Время и деньги
**Решение:** источник времени — `now()` в Postgres; на фронт отдаётся серверное время,
таймер считается по смещению. Деньги — BIGINT в минимальных единицах.

## ADR-010. Фоновые задачи на состоянии БД
**Решение:** asyncio-циклы (свипер броней, сверка платежей, закрытие распродаж, отправка outbox)
выбирают работу запросами к БД, а не из таймеров в памяти; для параллельных воркеров —
`FOR UPDATE SKIP LOCKED`.
**Почему:** переживает перезапуск сервера; простоя ничего не теряет — просроченное обработается при старте.
**Альтернативы:** Celery/APScheduler с брокером — лишняя инфраструктура для этого объёма.

## ADR-011. Тесты — на отдельной базе того же Postgres, пересоздаваемой каждый прогон
**Дата:** 2026-10-09
**Контекст:** CLAUDE.md требует гонять тесты на реальном Postgres, в том числе тесты
конкурентных запросов (несколько соединений, видящих коммиты друг друга). При этом
рабочая база не должна страдать от прогона тестов.
**Решение:** отдельная база на том же контейнере Postgres — `<рабочая>_test`
(или `TEST_DATABASE_URL`). Session-фикстура подключается к служебной базе `postgres`
в режиме AUTOCOMMIT (`CREATE DATABASE` нельзя внутри транзакции), делает
`DROP DATABASE IF EXISTS ... WITH (FORCE)` + `CREATE DATABASE`, подменяет `DATABASE_URL`
в окружении, сбрасывает кэши `get_settings` и engine, после прогона удаляет базу.
**Защита от сноса рабочей базы:** имя тестовой базы обязано заканчиваться на `_test`,
отличаться от базы из `DATABASE_URL` и соответствовать `[A-Za-z0-9_]+` (имя подставляется
в SQL как идентификатор). Иначе — `RuntimeError` до первого запроса к БД.
**Альтернативы:**
- откат транзакции вместо чистой базы — не годится для тестов конкурентности:
  параллельные соединения не видят незакоммиченных данных друг друга;
- схема на тест — не проверяет миграции целиком;
- отдельный контейнер Postgres для тестов — лишний сервис и дольше старт.
**Последствия:** прогон тестов требует прав на `CREATE DATABASE` (у владельца базы они есть);
на шаге миграций в ту же фикстуру добавится `alembic upgrade head`.

## ADR-012. Alembic: async-конфигурация, URL из настроек, явные имена ограничений
**Дата:** 2026-10-09
**Контекст:** весь бэк асинхронный (ADR-001), схема меняется только миграциями,
а тестовая фикстура должна накатывать их внутри уже работающего event loop.
**Решение:**
- `migrations/env.py` работает в двух режимах: обычный создаёт свой `AsyncEngine`,
  а при переданном `config.attributes["connection"]` использует готовое соединение.
  Второй режим нужен тестам: `asyncio.run()` внутри работающего loop вызвать нельзя.
- Адрес БД берётся из настроек приложения (`app.core.config`), в `alembic.ini`
  ключа `sqlalchemy.url` нет вообще — один источник правды и никаких секретов в файлах.
- `compare_type=True` и `compare_server_default=True`: без них autogenerate молча
  пропускает изменения типов и дефолтов.
- Имена ограничений и индексов задаёт `naming_convention` в `MetaData`.
- Тестовая схема создаётся миграциями, а не `Base.metadata.create_all()`.
**Альтернативы:**
- синхронный engine только для миграций — второй драйвер и вторая строка подключения;
- `create_all()` в тестах — быстрее, но тесты проверяли бы схему, которой нет на рабочей базе,
  а частичные индексы и CHECK из миграции остались бы непроверенными;
- `sqlalchemy.url` в `alembic.ini` — дублирование настроек и пароль в файле;
- имена ограничений по умолчанию — `downgrade` ломается, т.к. Postgres генерирует их сам.
**Последствия:** `alembic check` в CI поймает расхождение моделей и миграций;
фикстура и команда `alembic upgrade head` идут одним и тем же кодом env.py.

## ADR-013. Токены: PyJWT, HS256, без состояния на сервере
**Дата:** 2026-10-09
**Контекст:** вход по email без пароля (ADR-007), нужен способ подтверждать,
кто делает запрос. Серверных сессий не хотим — лишнее состояние и ещё одна таблица.
**Решение:** PyJWT, HS256, секрет и срок жизни из настроек. Claims `sub`, `iat`, `exp`;
при проверке `options={"require": ["sub", "exp"]}` — токен без `exp` жил бы вечно.
Передача через `Authorization: Bearer`, зависимость `get_current_user` на `HTTPBearer`
с `auto_error=False` (со включённым автоответом отсутствие заголовка даёт 403, а нужен 401).
`JWT_SECRET` без дефолта в коде: пустой секрет должен ронять старт, а не молча
подписывать токены предсказуемым ключом.
**Альтернативы:** `python-jose` (прежняя рекомендация FastAPI — тяжелее, тянет
`cryptography`, были провалы в поддержке); `authlib` (целый OAuth-фреймворк);
самописный HMAC (нет причин); серверные сессии в БД или Redis (лишнее состояние).
**Последствия:** отозвать отдельный токен нельзя — только сменить секрет. Для
тестового задания приемлемо; при появлении настоящей аутентификации понадобится
список отзыва или короткий срок жизни плюс refresh.

## ADR-014. Статус распродажи и остаток считает Postgres
**Дата:** 2026-10-09
**Контекст:** инвариант 2 — время решает сервер. Статус `upcoming/active/ended`
и остаток нельзя считать по часам Python: остаток обязан быть согласован
со счётчиками на тот же момент, что и проверка времени.
**Решение:** оба значения приходят из SQL — `case` по `now()` и
`quantity - sold - held`. Границы совпадают с условием резерва из `DATA_MODEL.md`
(`now() >= start_at AND now() < end_at AND closed_at IS NULL`): в момент старта
распродажа уже `active`, в момент `end_at` — уже `ended`, заполненный `closed_at`
тоже даёт `ended`. В ответе отдаётся `server_time` — фронт считает таймер
по смещению, не доверяя часам браузера (ADR-009).
**Альтернативы:** считать статус в Python по `datetime.now(UTC)` — часы процесса
и БД расходятся, и UI показывал бы активную кнопку, когда резерв уже отказывает;
считать на фронте — то же, только хуже.
**Последствия:** фронт не вычисляет статус сам, а берёт его из ответа;
проверка границ в тестах задаёт окна выражениями от `now()` в БД.

## ADR-015. Фронт и бэк — два отдельных сервиса, общаются по сети
**Дата:** 2026-10-09
**Контекст:** фронт нужно как-то соединить с API. Обычные варианты — прокси
в dev-сервере Vite, раздача собранной статики из FastAPI или отдельный сервис.
**Решение:** `frontend` — отдельный сервис в compose. Адрес бэкенда приходит
**только** из `VITE_API_URL` (по умолчанию `http://localhost:8000`); прокси Vite
не настраивается, FastAPI статику не раздаёт. Все запросы идут через один модуль
`src/api` — вызовов `fetch` в остальном коде нет.

Важно: `VITE_API_URL` — адрес **хостовой**, не `http://backend:8000`. Запрос делает
браузер, а он имени сервиса compose не разрешает.

**Альтернативы:**
- прокси Vite (`server.proxy`) — в разработке запросы идут на тот же origin,
  CORS не проверяется вообще, и на продакшене он ломается впервые;
- раздача статики из FastAPI — бэкенд начинает отвечать за сборку фронта,
  пропадает hot reload, а деплой фронта и API перестаёт быть независимым.

**Последствия:** CORS обязателен и проверяется с первого дня — `CORS_ORIGINS`
на бэкенде должен содержать адрес фронта. Фронт можно собрать и выложить
куда угодно, указав другой `VITE_API_URL`.

**Токен** хранится в `localStorage`: при хранении только в памяти вход терялся бы
на каждом обновлении страницы. Компромисс — уязвимость к XSS; для тестового
задания принят осознанно, вместе с остальными упрощениями ADR-007.

## ADR-016. Миграции применяются в entrypoint контейнера backend
**Дата:** 2026-10-09
**Контекст:** запуск на чистой машине должен сводиться к `make up` — отдельная команда
`alembic upgrade head` это лишний шаг, о котором легко забыть. При этом сервис никогда
не должен работать на схеме, не соответствующей коду.
**Решение:** `backend/docker-entrypoint.sh` с `set -e` выполняет `alembic upgrade head`
и затем `exec "$@"` (uvicorn). Падение миграции завершает скрипт с ошибкой, до `exec`
дело не доходит — контейнер не стартует. Postgres к этому моменту уже `healthy`
благодаря `depends_on: condition: service_healthy`.
**Альтернативы:**
- отдельный сервис `migrate` с `depends_on: condition: service_completed_successfully` —
  правильнее при нескольких репликах backend, но требование шага было про старт backend;
- `CMD sh -c "alembic upgrade head && uvicorn ..."` — `sh` остаётся PID 1 и хуже
  пробрасывает сигналы остановки;
- оставить ручной шаг — ревьюер получает лишнюю команду и возможность забыть её.
**Последствия:** `docker compose exec` через entrypoint не проходит, поэтому `make test`
и `make seed` миграции не перезапускают. **Ограничение:** при нескольких репликах backend
одновременные `alembic upgrade head` могут конфликтовать — тогда нужно переходить
на отдельный сервис миграций.

## ADR-017. Порт Postgres на хост по умолчанию не публикуется
**Дата:** 2026-10-09
**Контекст:** `POSTGRES_PORT=5432` в шаблоне ломал запуск на любой машине, где уже есть
локальный Postgres или контейнер другого проекта на 5432 — причём на первом же шаге
инструкции. При этом в задокументированном сценарии этот порт не нужен никому:
браузер ходит на 8000, backend внутри сети на `postgres:5432`, тесты идут внутри
контейнера, psql запускается через `docker compose exec postgres psql`.
**Решение:** в `docker-compose.yml` у сервиса `postgres` нет секции `ports`. Кому нужен
внешний psql или GUI-клиент — копирует `docker-compose.override.example.yml`
в `docker-compose.override.yml` (compose подхватывает его автоматически, файл в `.gitignore`).
Порт берётся из `POSTGRES_PORT`, по умолчанию 5433.
**Альтернативы:** оставить 5432 и описать проблему в README (ревьюер всё равно
спотыкается); сменить дефолт на 5433 (менее вероятно занят, но гарантии нет);
`ports: "127.0.0.1::5432"` со случайным портом (адрес пришлось бы каждый раз узнавать).
**Последствия:** `make up` на чистой машине не зависит от того, что занято на 5432.
Доступ к базе с хоста требует одного дополнительного шага, описанного в README.

## ADR-018. Единый порядок захвата блокировок: sales → reservations → orders → payments
**Дата:** 2026-10-10
**Контекст:** тест на конкурентность (шаг 2.3) поймал `deadlock detected`, когда один
покупатель одновременно отменяет бронь и бронирует снова. Резерв и отмена трогали
те же две строки, но в противоположном порядке:

| операция | первый захват | второй захват |
|---|---|---|
| резерв | строка `sales` (`held = held + 1`) | уникальный индекс по `reservations` (`INSERT`) |
| отмена | строка `reservations` (`status = 'cancelled'`) | строка `sales` (`held = held - 1`) |

Лог Postgres:
```
ERROR: deadlock detected
DETAIL: Process 60226 waits for ShareLock on transaction 2284; blocked by process 60220.
        Process 60220 waits for ShareLock on transaction 2283; blocked by process 60226.
        Process 60226: insert into reservations (...)
        Process 60220: update sales set held = held - 1 where id = $1
CONTEXT: while inserting index tuple in relation "uq_reservations_sale_id_user_id_active"
```
Резерв держал `sales` и ждал, пока отмена отпустит строку брони (вставка в частичный
уникальный индекс натыкалась на ещё не закоммиченную `held`-бронь того же покупателя);
отмена держала бронь и ждала `sales`. Через HTTP «отменить и сразу забронировать снова»
давало **HTTP 500 в 5 раундах из 8**: `DBAPIError` не является `IntegrityError`,
поэтому обработчик его не ловил. Данные при этом оставались согласованными —
Postgres откатывает проигравшую транзакцию целиком, — то есть это отказ
в обслуживании, а не оверсейл.

**Решение:** зафиксировать единый порядок захвата для всех операций —
`sales` → `reservations` → `orders` → `payments` (инвариант 10 в CLAUDE.md).
Отмена приведена к нему: `sale_id` брони читается обычным `SELECT` без блокировки
(поле неизменяемое, это безопасно), затем `SELECT ... FROM sales ... FOR UPDATE`,
и только потом тот же условный `UPDATE reservations ... WHERE status = 'held'`.
Решение «можно ли отменять» по-прежнему принимает условный UPDATE — захват строки
`sales` лишь выстраивает порядок и ничего не решает.

**Альтернативы:**
- **ретрай при `SQLSTATE 40P01`** — лечит симптом, инверсия порядка остаётся
  и всплывёт снова на оплате и свипере, где таблиц станет четыре. Ретраи ещё
  и маскируют проблему: в логах видно только замедление;
- **отдавать 409 `retry_later`** — честно, но перекладывает ретрай на клиента
  в совершенно штатном сценарии «передумал и беру снова»;
- **отложенный уникальный индекс** — невозможно: частичные уникальные индексы
  в Postgres нельзя объявить `DEFERRABLE`;
- **одна общая блокировка на распродажу** (advisory lock) — сериализует вообще всё,
  включая независимые операции разных покупателей.

**Последствия:** отмена делает на один запрос больше (`SELECT` + `FOR UPDATE`).
Взамен — ни одного дедлока: тест №3 прошёл 20 раз подряд, HTTP-прогон из 30 раундов
дал 0 пятисоток (было 5 из 8). Порядок обязателен для свипера и оплаты: там
добавятся `orders` и `payments`, и любая операция, берущая несколько таблиц,
должна идти по цепочке слева направо.

## ADR-019. Свипер: от двойного возврата спасает условный UPDATE, FOR UPDATE — от дедлока
**Дата:** 2026-10-10
**Контекст:** истёкшие брони в `held` должны возвращать единицу на витрину
(инвариант 3). Экземпляров backend может быть несколько, значит свиперов тоже —
и одна бронь не должна вернуть единицу дважды. ADR-010 упоминал
`FOR UPDATE SKIP LOCKED` для параллельных воркеров, и надо было решить, что
здесь действительно нужно.
**Решение:** `sweep_expired_once` — обычный `SELECT DISTINCT sale_id` без
блокировки (только чтобы узнать объём работы), затем на каждую распродажу
своя транзакция: `SELECT ... FROM sales ... FOR UPDATE` → условный
`UPDATE reservations SET status = 'expired' WHERE sale_id AND status = 'held'
AND expires_at <= now() RETURNING id` → `held = held - <число вернувшихся строк>`.

**Два механизма, которые легко спутать:**
- **От двойного возврата спасает условный UPDATE, а не блокировка.** `RETURNING`
  отдаёт ровно те брони, которые перевела в `expired` именно эта транзакция.
  Второй свипер ждёт блокировку строки брони, после коммита первого
  перепроверяет условие (READ COMMITTED) и видит `expired` — строка не попадает
  в его `RETURNING`, и он уменьшает счётчик на 0. Это работало бы и без
  `FOR UPDATE` на `sales`.
- **`FOR UPDATE` на `sales` нужен для инварианта 10.** Без него свипер брал бы
  `reservations` раньше `sales`, то есть в обратном порядке относительно резерва,
  и мы получили бы тот же дедлок, что поймали на шаге 2.3 (ADR-018). Это защита
  от дедлока, а не от двойного возврата.
- **`status = 'held'` в условии заодно оберегает `paying`** — инвариант 4:
  начатая оплата доводится до конца, срок её не касается.

**`SKIP LOCKED` сознательно не используется.** Он избавил бы свипер от ожидания,
но транзакции резерва и отмены очень короткие (несколько операторов, без сетевых
вызовов), так что ожидание ничтожно. Взамен гарантия остаётся простой и жёсткой:
бронь возвращается не позже чем `RESERVATION_TTL_SECONDS + SWEEPER_INTERVAL_SECONDS`.
С `SKIP LOCKED` занятая распродажа пропускалась бы до следующего тика, и обещание
пришлось бы ослабить до `TTL + k·интервала`. **Условие пересмотра:** если тик
начнёт конкурировать с долгими транзакциями (например, оплата будет держать
`sales` дольше) или перестанет успевать за один проход — переходим на `SKIP LOCKED`
и ослабляем формулировку гарантии.

**Транзакция на распродажу, а не на весь проход:** иначе одна долгая строка
держала бы блокировки на всех остальных распродажах.

**Выключатель — явный флаг `SWEEPER_ENABLED`, а не интервал.** Нулевой интервал
не отключает свипер, а роняет старт приложения (`Field(gt=0)` → `ValidationError`):
случайный ноль в конфиге не должен молча останавливать возврат броней. При
`SWEEPER_ENABLED=false` в лог уходит WARNING о том, что единицы останутся занятыми.

**Альтернативы:** таймер на каждую бронь в памяти (теряется при перезапуске,
не работает с несколькими экземплярами — отвергнуто ещё в ADR-010); `pg_cron`
или внешний планировщик (лишняя инфраструктура, и логика уехала бы из кода);
снимать бронь лениво при чтении витрины (остаток зависел бы от того, зашёл ли
кто-нибудь на страницу).

**Последствия:** `sweep_expired_once` отделён от цикла и тестируется напрямую,
без ожидания настоящего TTL. Любая будущая операция со счётчиками (оплата)
обязана брать `sales` первой — иначе инверсия вернёт дедлок.

## ADR-020. Сигнал о смене остатка отправляет триггер в БД, а не код сервисов
**Дата:** 2026-10-10
**Контекст:** уточняет ADR-003. Остаток нужно рассылать по WebSocket, и главный
критерий выбора — **новые операции не должны иметь шанса забыть уведомление**:
оплата и закрытие распродажи это новый код, и пропущенную строчку в нём легко
не заметить, а тест на забытое уведомление забудут вместе с вызовом.

**Решение:** триггер `sale_changed_notify` на `UPDATE sales` вызывает
`pg_notify('sale_changed', new.id::text)`. Гарантию даёт БД: кто бы и откуда
ни изменил счётчики, сигнал уйдёт.
- `WHEN` ограничивает поля, из которых складывается публичный снимок:
  `quantity, sold, held, start_at, end_at, closed_at`. Правки цены из seed
  витрину не меняют и сигнала не дают.
- **Сигнал внутри транзакции — это и есть «только при коммите».** Postgres
  доставляет уведомления при коммите и выбрасывает при откате, поэтому отказ
  резерва (`sold_out`, `already_reserved`) сигнала не даёт. Это надёжнее
  формулировки ADR-003 «после коммита бэк делает NOTIFY»: там между коммитом
  и вызовом есть окно, в котором процесс может умереть и уведомление
  потеряется навсегда.
- Одинаковые `(канал, payload)` внутри одной транзакции Postgres склеивает сам.

**В сигнале только `sale_id`.** Получатель перечитывает состояние из БД. Это
не экономия трафика, а защита от «прыжка назад»: при обгоне сигналов в рассылку
всё равно уйдёт то, что в базе сейчас, а не устаревшая копия из сообщения.

**Склейка пачки.** Сигналы собираются в множество «грязных» распродаж; рабочая
задача просыпается, ждёт `LIVE_UPDATE_WINDOW_MS` (по умолчанию 50) и обрабатывает
всё накопившееся одной пачкой: десять броней за окно дают один запрос к БД
и одну рассылку. Распродажи, на которые никто не подписан, не читаются вовсе.

**Доставка — очередь на подписчика размером 1.** Снимок самодостаточен, поэтому
у медленного клиента содержимое очереди заменяется, а не копится: он получает
свежее состояние и не тормозит рассылку остальным.

**Слушатель — отдельное соединение asyncpg вне пула:** `LISTEN` занимает
соединение навсегда, возвращать его в пул нельзя. При разрыве — переподключение
и **рассылка свежих снимков всем, на кого есть подписка**: сигналы за время
разрыва потеряны, и перечитать состояние — единственный честный способ не
оставить клиента с устаревшим остатком.

**Альтернативы:**
- **явный вызов в каждом сервисе** — проигрывает по главному критерию: забыть
  легко, а заметить трудно. Отвергнуто;
- **публикация после коммита из кода** — окно между коммитом и отправкой;
- **отправка самого состояния в payload** — «прыжок назад» при обгоне сообщений,
  плюс лимит payload в 8000 байт;
- **polling с фронта** — задержка и постоянная нагрузка (ADR-003);
- **Redis pub/sub** — лишний сервис при наличии LISTEN/NOTIFY (ADR-003).

**Последствия:** логика уведомления живёт в миграции, а не в коде сервисов —
менее заметна, поэтому описана здесь, в `DATA_MODEL.md` и в комментарии самой
миграции. Сессию БД в WebSocket-эндпоинте нельзя брать через зависимость:
соединение из пула было бы занято всё время, пока клиент смотрит страницу,
и пятнадцать зрителей исчерпали бы пул целиком — снимок читается отдельной
короткоживущей сессией.

## ADR-021. Заглушка платёжки — отдельный сервис со своим хранилищем и своим кодом
**Дата:** 2026-10-12
**Контекст:** уточняет ADR-005. Нужно решить, насколько заглушка отделена
от основного сервиса: общий код и общая БД или полная изоляция.
**Решение:** `payment-stub/` — самостоятельный сервис: свой `pyproject.toml`,
свой lock-файл, свой `Dockerfile`, **своё хранилище SQLite** в отдельном volume.
Ничего из `backend/` не переиспользуется.
**Почему:** заглушка изображает чужую систему. Если дать ей общий код и общую
БД, перестанет проверяться именно то, ради чего она существует: сетевые сбои
между сервисами, асинхронный ответ вебхуком, независимый перезапуск и чужая
схема данных. Общая БД к тому же позволила бы бэкенду «подсмотреть» состояние
платежа напрямую — а в жизни такой возможности нет.
SQLAlchemy не взят: в заглушке несколько простых запросов, `aiosqlite`
достаточно. Миграций нет намеренно — схема создаётся при старте, историю чужой
БД мы не ведём.

**Идемпотентность** держит `UNIQUE (idempotency_key)`, а не чтение перед
записью — тот же приём, что в основном сервисе. Первый вызов отвечает **202**,
повторный с тем же ключом — **200** и тот же платёж: клиенту видно, создан
платёж сейчас или уже был. Тот же ключ с другой суммой или валютой — **409**
`amount_mismatch`.

**Срок разрешения хранится в БД (`payments.resolve_at`), а не только в задаче.**
Задержка отрабатывается фоновой задачей, и она не переживает перезапуск
контейнера: платёж, созданный в режиме approve с задержкой, завис бы навсегда,
хотя режим `hang` никто не включал. Поэтому при старте просроченные платежи
доделываются, а недождавшиеся планируются на остаток срока. Платежи в режиме
`hang` не трогаются — у них `resolve_at` пустой, они ждут только ручного
решения через `POST /payments/{id}/resolve`.

**Подпись вебхука** считается от тех самых байтов, которые уходят в теле:
пересчёт из разобранного JSON дал бы другой порядок ключей, и подпись
не сошлась бы на принимающей стороне. Заголовок `X-Signature: sha256=<hex>`,
секрет общий через окружение.

**Вебхук может потеряться — это осознанно.** Повторы идут с нарастающей паузой
(5 попыток, 0.5 → 1 → 2 → 4 → 8 с), после чего заглушка сдаётся и пишет ошибку
в лог. Статус платежа при этом остаётся окончательным и доступен через
`GET /payments/{id}`. Потерю закрывает **сверка статуса на стороне backend**
(следующие шаги дня 3): бэкенд периодически доспрашивает платежи, по которым
не получил результат. Делать доставку гарантированной внутри заглушки
бессмысленно — настоящие платёжные провайдеры тоже теряют вебхуки, и backend
обязан быть к этому готов.

**Альтернативы:**
- **заглушка внутри backend** (отвергнуто ещё в ADR-005): не проверяет сетевые
  сбои и асинхронность ответа;
- **общая БД с основным сервисом**: бэкенд мог бы читать состояние платежа
  напрямую, минуя API, и тесты перестали бы отражать реальность;
- **общий код моделей и настроек**: связность, из-за которой правка в backend
  неожиданно меняет поведение «чужой» системы;
- **гарантированная доставка вебхуков** (очередь с персистентными повторами):
  усложняет заглушку и, главное, снимает с backend обязанность сверять статус —
  а именно её и нужно проверить.

**Последствия:** у заглушки свой прогон тестов (`make test` и `make lint`
включают оба сервиса) и свой `uv.lock`. Backend на этом шаге не менялся:
переменные `PAYMENT_STUB_URL` и `PAYMENT_CALLBACK_BASE_URL` добавлены
в `.env.example` заранее, чтобы следующий шаг не начинался с правки окружения.

## ADR-022. Оплата: детерминированный ключ идемпотентности и вызов провайдера вне транзакции
**Дата:** 2026-10-12
**Контекст:** оплата затрагивает четыре таблицы (`sales`, `reservations`,
`orders`, `payments`) и вызывает чужую систему. Нужно решить, где заканчивается
транзакция, откуда берётся ключ идемпотентности и по чему вебхук находит платёж.

**Решение 1. Ключ идемпотентности выводится из брони: `pay:<reservation_id>`.**
Не случайный UUID. Тогда повторный «Оплатить» и повтор после сетевого сбоя
приходят к провайдеру с тем же ключом, и он возвращает **тот же** платёж,
а не создаёт второй (ADR-021). Случайный ключ при повторе создал бы у провайдера
второй платёж, и мы получили бы два вебхука на один заказ.
*Альтернатива:* генерировать ключ и хранить его до вызова — то же самое, но
с лишней записью; при потере ответа ключ пришлось бы восстанавливать из БД.

**Решение 2. Вызов провайдера — строго после коммита, вне транзакции.**
CLAUDE.md требует, чтобы сетевой вызов не держал блокировки БД. Это возможно
именно потому, что бронь в `paying` не истекает (инвариант 4): к моменту ответа
провайдера бронь никуда не денется, даже если прошло больше TTL.
*Последствие:* между коммитом и вызовом есть окно. Если процесс умрёт в нём,
заказ останется `pending_payment` без платежа у провайдера — это закрывает
сверка (шаг 9) и повторный «Оплатить», который снова зовёт провайдера с тем же
ключом.
*Альтернатива:* звать провайдера внутри транзакции — блокировка строки `sales`
держалась бы всё время сетевого запроса, и резерв с отменой встали бы в очередь
за чужой системой.

**Решение 3. Недоступность провайдера — не 500, а 202 `awaiting_provider`.**
Заказ создан, бронь в `paying`, единица удержана. Клиент видит «ожидаем
платёжную систему». Отдавать 500 означало бы соврать: наша часть работы
выполнена и зафиксирована.

**Решение 4. Вебхук ищет платёж по НАШЕМУ `idempotency_key`, а не по
`provider_payment_id`.** Ответ на создание платежа мог не дойти — тогда
`provider_payment_id` у нас пустой, и по нему платёж найти нельзя. Ключ же
известен заранее, он выводится из брони. `provider_payment_id` дозаписывается
из вебхука через `coalesce`. Есть тест: заглушка создала платёж, ответ
не дошёл, вебхук всё равно завершает заказ.

**Решение 5. Применение результата — отдельная функция `apply_payment_result`,
решение принимает условный `UPDATE payments WHERE status = 'pending'`.**
Два одновременных вебхука: второй получит 0 строк и ничего не изменит, поэтому
`sold + 1` произойдёт один раз. Ту же функцию позовёт сверка зависших платежей
(шаг 9) — отсюда и отдельная функция, а не код внутри обработчика.
Уже обработанный вебхук получает **200**, а не ошибку: иначе провайдер
продолжал бы повторять то, что мы уже применили.

**Порядок блокировок** в обеих операциях — инвариант 10: `sales` → `reservations`
→ `orders` → `payments`. `sale_id` и `reservation_id` читаются обычным `SELECT`
(они неизменяемы), затем берётся `SELECT ... FROM sales ... FOR UPDATE`.
Проверено тестом: вебхук, резерв и отмена на одной распродаже одновременно,
20 прогонов, ни одного дедлока.

**Письмо** кладётся в `outbox` в той же транзакции, что и смена статуса, с
`dedup_key = order_paid:<order_id>` и `ON CONFLICT DO NOTHING` (ADR-004,
инвариант 6). Повторный вебхук второй строки не добавит — проверено
и тестом, и живым прогоном с `duplicate_webhooks`.

## ADR-023. Сверка зависших платежей: переспрос тем же ключом и SKIP LOCKED при выборке
**Дата:** 2026-10-12
**Контекст:** вебхук может потеряться — у заглушки повторы не бесконечны
(ADR-021), да и ответ на создание платежа мог не дойти (ADR-022). Значит заказ
может навсегда остаться `pending_payment`, а единица — удержанной. Нужен процесс,
который доспрашивает провайдера сам.

**Решение 1. Переспрос — тот же `POST /payments` с тем же `idempotency_key`,
а не `GET /payments/{id}`.** Одна операция закрывает оба случая: известный
платёж вернётся с текущим статусом, а неизвестный (создание не дошло) будет
создан сейчас. `GET` по `provider_payment_id` во втором случае не сработал бы —
этого id у нас нет.
Поведение заглушки **проверено вживую** перед реализацией, а не предположено:
первый `POST` вернул `202` со `status: pending`, повторный с тем же ключом —
`200` со `status: succeeded`. То есть повтор отдаёт актуальный статус.

**Решение 2. Кандидаты занимаются через `FOR UPDATE ... SKIP LOCKED`.**
Несколько экземпляров backend: первый блокирует строки, второй их пропускает
(не ждёт) и берёт другие. Провайдера дёргают один раз на платёж.
Это **оптимизация, а не защита корректности**: корректность держит условный
`UPDATE payments WHERE status = 'pending'` в `apply_payment_result` — если две
сверки всё же дойдут до конца, вторая получит 0 строк и ничего не изменит.
В отличие от свипера (ADR-019), здесь `SKIP LOCKED` уместен: пропустить платёж
не страшно, его возьмёт следующий тик или другой экземпляр, а гарантия по срокам
задаётся потолком интервала, а не каждым проходом.

**Явное исключение из инварианта 10.** Транзакция выборки кандидатов блокирует
`payments`, **не беря `sales` первой**. Это отступление от порядка
`sales → reservations → orders → payments`, и оно допустимо потому, что:
1. затронута ровно одна таблица — цикла ожиданий не образуется;
2. `SKIP LOCKED` не ждёт занятых строк, а пропускает их;
3. транзакция немедленно коммитится, до любых сетевых вызовов.

**Добавлять в эту транзакцию другие таблицы нельзя** — это сразу вернёт риск
дедлока, который мы ловили на шаге 2.3 (ADR-018). Исключение записано
в CLAUDE.md рядом с инвариантом 10 и в комментарии к самому SQL.

**Решение 3. `last_checked_at` отмечается ДО сетевого вызова**, в той же
короткой транзакции, что и выборка. Если провайдер не ответит, платёж не будет
опрошен повторно сию же секунду. Нарастающий интервал считается в SQL:
`base * 2^reconcile_attempts`, но не больше потолка.

**Решение 4. `reconcile_attempts` хранится в БД, а не в памяти.** По той же
причине, что `resolve_at` в заглушке: перезапуск backend не должен сбрасывать
прогресс, иначе после каждого рестарта зависшие платежи опрашивались бы заново
с минимальной паузой.

**Решение 5. Льготный период (`RECONCILE_GRACE_SECONDS`).** Свежим платежам
даём шанс получить вебхук, не дёргая провайдера зря: нормальный путь — вебхук,
сверка это страховка.

**`hang` ждём сколько угодно.** Платёж, который провайдер не решает, остаётся
`pending`, а заказ не отменяется: инвариант 4 — начатая оплата доводится
до конца. Единица остаётся удержанной, свипер её не трогает.

**Гарантия для клиента:** при потерянном вебхуке заказ досчитывается не позже
чем через `RECONCILE_BACKOFF_MAX_SECONDS` (по умолчанию 5 минут) — это потолок
интервала между проверками одного платежа.

**Альтернативы:**
- **`GET /payments/{id}`** — не работает, когда создание платежа не дошло
  и `provider_payment_id` пустой;
- **без `SKIP LOCKED`, просто условный UPDATE** — корректно, но два экземпляра
  дёргали бы провайдера по одному платежу;
- **`SELECT` без блокировки + полагаться только на условный UPDATE** — то же,
  плюс лишние сетевые вызовы;
- **отменять заказ по таймауту** — нарушило бы инвариант 4: провайдер может
  ответить позже, и тогда деньги списаны, а бронь снята;
- **очередь задач вместо опроса БД** — лишняя инфраструктура (ADR-010).

## ADR-024. Доставка писем: at-least-once с дедупликацией по Message-ID
**Дата:** 2026-10-12
**Контекст:** `outbox` наполняется в одной транзакции со сменой статуса
(ADR-004, инвариант 6) — запись письма строго одна. Остаётся доставка,
и у неё есть неустранимое окно: между «SMTP принял письмо» и «отметили sent»
нет общей транзакции. Падение процесса ровно в этом окне даёт либо потерю
письма, либо его дубль. Третьего варианта не существует.

**Решение: выбран дубль, а не потеря.** Потерянное письмо об оплате означает,
что покупатель заплатил и не узнал об этом — восстановить это невозможно, он
пойдёт в поддержку. Второе такое же письмо неприятно, но безвредно.

**Честная граница гарантии:**
- запись в `outbox` — **ровно одна** на событие (уникальный `dedup_key`,
  `ON CONFLICT DO NOTHING`); повторный вебхук и сверка второй строки не создают;
- доставка — **at-least-once** с дедупликацией по `Message-ID`, не exactly-once.

`Message-ID` постоянный и выводится из `dedup_key`:
`<order_paid.{order_id}@flash-sale.local>`. Поэтому повтор того же письма имеет
тот же идентификатор, и получающая сторона может его опознать и подавить.
Инвариант 6 («каждое письмо отправляется ровно один раз») выполняется в части
записи и в штатной работе; формулировка «не более одного при нормальной работе,
возможен повтор с тем же Message-ID при падении между отправкой и фиксацией»
точнее описывает реальность. Это зафиксировано и в README.

**Окно минимизировано:** письмо собирается до взятия аренды, а за `send`
немедленно идёт `mark_sent`, без промежуточной работы.

**Решение 2. Таймаут SMTP обязан быть вдвое меньше аренды, и это проверяется
при старте.** Без такой проверки медленный SMTP давал бы дубль **в штатной
работе**, а не только при падении: аренда истекла бы, пока первый отправитель
ещё ждёт ответа, второй подхватил бы ту же строку и отправил письмо снова.
`model_validator` в настройках роняет старт с объяснением. По умолчанию
таймаут 10 с при аренде 30 с.

**Решение 3. Аренда (`locked_until`) вместо «взял и не отпустил».** Строка,
занятая упавшим процессом, возвращается в работу по истечении аренды — иначе
письмо осталось бы занятым навсегда. Выборка кандидатов берёт и строки
с истёкшей арендой.

**Решение 4. Шаблоны по `kind` в реестре.** Письмо собирается **только
из `payload` строки outbox** — отправитель не ходит в другие таблицы, поэтому
письмо остаётся тем, каким его задумали в момент события, даже если данные
потом изменились. Новый вид письма — новая функция и строка в реестре
(на следующем шаге появится письмо о закрытии распродажи). Неизвестный `kind`
или неполный `payload` → `failed` с причиной в `last_error`: повтор ничего
не изменит, а цикл должен продолжать работу.

**Решение 5. `aiosmtplib`, не `smtplib`.** Отправитель живёт в том же event
loop, что свипер, сверка и слушатель LISTEN. `smtplib` блокирует поток целиком,
и на время таймаута SMTP встали бы все фоновые задачи. `asyncio.to_thread`
сработал бы, но завёл бы второй стиль работы с внешними системами, тогда как
всё остальное в проекте асинхронное (ADR-001). Само письмо собирается через
`email.message.EmailMessage` из стандартной библиотеки — она корректно кодирует
русский текст и заголовки.

**Исключение из инварианта 10** — то же, что в ADR-023: транзакция выборки
блокирует только `outbox`, использует `SKIP LOCKED` и коммитится до отправки.
Добавлять в неё другие таблицы нельзя.

**Альтернативы:**
- **отмечать `sent` до отправки** — падение теряет письмо навсегда; отвергнуто
  ровно по выбранной стороне компромисса;
- **двухфазная отметка (`sending` → `sent`)** — не устраняет окно, только
  переносит его; при падении строка всё равно требует аренды, чтобы вернуться;
- **отправка прямо из обработчика вебхука** — письмо ушло бы при откате
  транзакции или дважды при повторе вебхука (ADR-004);
- **внешняя очередь писем** — лишняя инфраструктура, и та же граница гарантии.

## ADR-025. Закрытие распродажи: снимаем held, quantity не трогаем
**Дата:** 2026-10-12
**Контекст:** когда `end_at` прошёл, распродажа должна закрыться: покупать
нельзя, неоплаченные корзины очищаются. Требовалось решить, что именно значит
«непроданное снимается с продажи» и как это согласуется с инвариантом 4.

**Решение 1. `quantity` не изменяется.** Закрытие трогает только `held`
(снятые брони) и `closed_at`. «Не продано» считается как `quantity - sold` —
магазину нужна эта цифра после распродажи, а уменьшение `quantity` её бы
уничтожило. Купить нельзя не потому, что товара нет, а потому что
`closed_at IS NOT NULL` — это условие уже проверяет и резерв, и статус
распродажи (ADR-014).
*Альтернатива:* `quantity = sold` — витрина выглядела бы «распродано
полностью», что неправда, и отчёт стал бы невозможен.

**Решение 2. Брони в `paying` не снимаются** (инвариант 4). Начатая оплата
доводится до конца, и успешный вебхук после закрытия по-прежнему делает заказ
`paid`. Условие `status = 'held'` в UPDATE это и обеспечивает. Тест из шага 8
(`test_webhook_completes_order_after_sale_window_closed`) остался зелёным —
он писался специально, чтобы пережить этот шаг.

**Решение 3. Письмо «корзина очищена» — только владельцам `held`.**
У кого бронь в `paying`, оплата продолжается, и письмо «корзина очищена» было
бы неправдой; они получат письмо об оплате при успехе. `dedup_key` по **брони**
(`sale_closed_cart_released:<reservation_id>`), а не по распродаже: писем
столько, сколько очищенных корзин, и повторный проход вторых не добавляет
(`ON CONFLICT DO NOTHING`, инвариант 6).

**Решение 4. «Оплатить» после `end_at` → 409 `sale_ended`.** Новую оплату после
конца распродажи не начинаем, даже если воркер ещё не прошёл и бронь формально
жива. Условие окна добавлено **в тот же** условный `UPDATE`, который переводит
бронь в `paying`:
```sql
and exists (select 1 from sales s
            where s.id = r.sale_id and now() < s.end_at and s.closed_at is null)
```
Отдельное чтение дало бы зазор, в который распродажа успевает закрыться.
Условие стоит только на переходе `held → paying` — уже начатые оплаты
не затрагиваются.

**Решение 5. Защита от двух воркеров — повторная проверка условия под
блокировкой**, а не отдельный флаг:
```sql
select id from sales where id = :sale_id and end_at <= now() and closed_at is null
for update
```
Второй воркер, дождавшись блокировки, не найдёт строку (`closed_at` уже
заполнен) и ничего не сделает. Транзакция на распродажу, а не на весь проход —
как в свипере (ADR-019): иначе одна долгая строка держала бы блокировки
на всех остальных.

**Живое обновление приходит само.** Триггер `sale_changed_notify` следит
в том числе за `closed_at` (ADR-020), поэтому закрытие рассылает новый снимок
со статусом `ended` без единой строчки в коде закрытия. Это ровно то свойство,
ради которого триггер и выбирался вместо явного вызова. Два `UPDATE sales`
в одной транзакции (`held`, затем `closed_at`) дают **один** `NOTIFY`:
Postgres склеивает одинаковые `(канал, payload)` внутри транзакции.

**Порядок блокировок** — инвариант 10: `sales` → `reservations`. Проверено
тестом: закрытие и оплата той же брони одновременно, 20 прогонов, ни одного
дедлока; исход ровно один — либо бронь снята, либо оплата началась.

**Первый проход сразу при старте** (ADR-010): распродажи, закончившиеся
за время простоя сервера, закрываются при запуске, потому что работа выбирается
запросом к БД, а не таймерами в памяти.

## ADR-026. Дашборд магазина: агрегаты одним запросом, одно WS-соединение на все распродажи
**Дата:** 2026-10-12
**Контекст:** магазину нужен экран со своими распродажами: счётчики, выручка,
«не продано». Распродаж у магазина может быть десятки, и всё это должно
обновляться живьём.

**Решение 1. Агрегаты одним запросом через `LEFT JOIN LATERAL`.**
Выручка и число оплаченных заказов считаются рядом со строкой распродажи,
а не запросом на каждую. Есть тест, который считает запросы к `sales` через
событие `before_cursor_execute` и требует ровно один — N+1 поймается сразу,
если кто-то решит собрать выручку в цикле.
Частичный индекс `orders (sale_id) WHERE status = 'paid'`: без него подсчёт
просматривал бы всю таблицу заказов, а после нагрузочного скрипта их будет много.

**Решение 2. Выручка — только `orders.status = 'paid'`.** `pending_payment`
и `failed` не считаются: деньги получены только по оплаченным заказам. Это
в `WHERE` подзапроса, а не фильтром в Python.

**Решение 3. `unsold` заполняется только после закрытия.** Пока распродажа
идёт, «не продано» не имеет смысла — остаток ещё может уйти. До закрытия поле
`null`, после — `quantity - sold` (ADR-025: `quantity` при закрытии не меняется
именно ради этой цифры).

**Решение 4. Одно WS-соединение на несколько распродаж:
`WS /ws/sales?ids=<id>,<id>,...`.**
Per-sale подписка на дашборде расточительна: десять распродаж — десять TCP-соединений,
десять ASGI-задач, десять очередей на один экран. Хаб уже хранит подписчиков
как `dict[sale_id, set[Queue]]`, поэтому одна очередь просто регистрируется
под несколькими ключами — переделывать его не пришлось.

Формат кадров различается полем, а не формой: `{"type": "snapshot", "sales": [...]}`
при подключении (экран отрисовывается целиком) и `{"type": "update", "sale": {...}}`
на изменение. Клиент не угадывает по структуре.

Старый `WS /ws/sales/{id}` остался: страница распродажи им пользуется, и ломать
её незачем. Два эндпоинта над одним хабом.

**Границы и поведение при мусоре:**
- предел **100 уникальных** id на соединение, иначе закрытие с кодом `4413`
  и причиной. Лимит по уникальным: дубли не создают нагрузки и просто
  сворачиваются;
- неизвестные id и нераспознанный мусор **не ломают соединение** — их просто
  нет в снимке. На дашборде это нормальная ситуация: распродажу могли удалить.

**Решение 5. Выручка перезапрашивается по изменению `sold` в снимке.**
В снимке выручки нет (ADR-020: снимок — только изменяемая часть распродажи),
поэтому при смене `sold` строки перечитываются по HTTP, со склейкой 300 мс:
серия продаж даёт один запрос, а не по запросу на единицу. Изменения `held`
выручку не трогают, поэтому по ним не дёргаем.

**Известное ограничение.** Распродажа, созданная при открытом дашборде,
в подписку не попадёт: список и подписка формируются при загрузке. Пока
закрывается перезапросом при возврате на вкладку; полноценное решение —
событие «у магазина появилась распродажа», и оно записано в README
в «Что дальше».

**Альтернативы:**
- **коррелированные подзапросы в SELECT** вместо `LATERAL` — то же по смыслу,
  но хуже читается, когда агрегатов несколько;
- **выручка отдельным запросом по списку id** — второй круговой обход и
  рассинхронизация между счётчиками и деньгами;
- **per-sale WS-подписка на дашборде** — десятки соединений на экран;
- **один WS без списка, с рассылкой всех распродаж** — клиент получал бы
  чужие обновления, а сервер читал бы лишние строки;
- **подписка по `shop_id`** — выглядит проще, но сделала бы публичный сокет
  ролевым: пришлось бы передавать токен в WS и проверять права, тогда как
  данные распродажи и так публичны.

## ADR-001. Стек: FastAPI + PostgreSQL + React
**Дата:** <!-- Thu Oct  8 23:59:31 +06 2026 -->
**Контекст:** нужен отдельный backend и frontend, реляционная БД, WebSocket для live-обновлений.
**Решение:** FastAPI (async, WebSocket из коробки, Swagger как живая документация API),
SQLAlchemy 2 async + asyncpg, Alembic, PostgreSQL 16; React + Vite + TypeScript.
**Альтернативы:** Django (тяжелее, async слабее), Node.js/NestJS (меньше моего опыта).
**Последствия:** весь бэк асинхронный; для критичных операций пишем явный SQL.

## ADR-002. Резерв — атомарный условный UPDATE
**Контекст:** последнюю единицу нельзя продать двоим.
**Решение:** счётчики `sold`/`held` в `sales` и один `UPDATE ... WHERE sold + held < quantity RETURNING`.
Плюс CHECK-ограничение `sold + held <= quantity` как страховка.
**Альтернативы:** `SELECT ... FOR UPDATE` (корректно, но держит блокировку дольше и
сериализует всех на чтении); Redis-счётчик (ещё один источник правды, сложнее восстановление);
SERIALIZABLE (ретраи на каждом конфликте).

**Альтернатива «очередь» (asyncio.Lock / Redis / RabbitMQ) — почему не выбрали:**
- `asyncio.Lock` живёт в одном процессе. Два воркера uvicorn или два инстанса — и защиты
  нет; состояние блокировки умирает вместе с процессом. Это не защита, а её видимость.
- Redis-блокировка — ещё один источник правды и ещё один сервис. Срок жизни блокировки
  не связан с длительностью транзакции: если транзакция затянулась, блокировка истечёт
  и второй запрос войдёт в критическую секцию. Чтобы это закрыть, нужны fencing-токены
  и проверка владения — больше кода, чем сам резерв.
- Очередь команд резерва (RabbitMQ и подобное) даёт честный порядок обслуживания,
  но делает запрос асинхронным: клиенту нужен поллинг или push, чтобы узнать результат.
  Плюс брокер в инфраструктуре, плюс пропускная способность упирается в одного
  консьюмера, а `CHECK` в БД всё равно остаётся нужен как последняя линия защиты.
- Главное: Postgres **уже** сериализует условный `UPDATE` на блокировке строки.
  Очередь дублировала бы то, что БД делает бесплатно и переживая перезапуск.
- Очередь была бы оправдана, если бы требовался гарантированный порядок
  «кто первым нажал» или решение зависело от внешних систем. Здесь достаточно
  блокировки одной строки.

**Последствия:** счётчики должны меняться только вместе со статусом брони в одной транзакции;
есть тест на согласованность `held` = число броней в `held/paying`.
Важная деталь, выясненная на шаге 2.1: `CHECK (sold + held <= quantity)` спасает **только**
если запись — инкремент (`held = held + 1`). Наивная версия писала посчитанное в Python
абсолютное значение, и `CHECK` молчал: оба запроса писали `held = 1`, `0 + 1 <= 1` проходило
дважды. При инкременте та же гонка упирается в `ck_sales_not_oversold` — проверено
намеренной поломкой условия в `UPDATE`.

## ADR-003. Live-обновления: WebSocket + Postgres LISTEN/NOTIFY
**Решение:** после коммита изменения остатков бэк делает `NOTIFY`, слушатель рассылает событие
всем WebSocket-клиентам распродажи.
**Альтернативы:** in-memory pub/sub (не работает с несколькими инстансами), Redis pub/sub
(лишний сервис), polling (задержка и нагрузка).
**Последствия:** клиент после переподключения запрашивает актуальное состояние по HTTP.

## ADR-004. Ровно одно письмо: transactional outbox
**Решение:** письмо пишется в `outbox` с уникальным `dedup_key` в той же транзакции,
что и смена статуса; отдельный цикл отправляет pending в SMTP.
**Альтернативы:** отправка прямо из обработчика (письмо может уйти при откате транзакции
или уйти дважды при повторе вебхука).
**Последствия:** гарантия «не более одного письма на событие»; при падении SMTP — ретраи.

## ADR-005. Платёжная заглушка — отдельный сервис
**Решение:** `payment-stub` на FastAPI: режимы approve / decline / hang, задержка,
ответ вебхуком + эндпоинт статуса. Бэк при зависании периодически сверяет статус сам.
**Альтернативы:** заглушка внутри бэка (не проверяет сетевые сбои и асинхронность ответа).

## ADR-006. Почта: Mailpit
**Решение:** настоящий SMTP в Mailpit, письма видны в веб-UI — «ровно одно письмо» проверяется глазами и тестом через API Mailpit.

## ADR-007. Упрощённый вход
**Решение:** вход по email без пароля → подписанный токен (JWT). Роли `buyer` / `shop`.
**Почему:** задание разрешает; фокус на конкурентности, а не на аутентификации.
**Следующий шаг:** magic link по почте или пароль.

## ADR-008. Одна бронь = одна единица, одна единица на покупателя
**Решение:** частичный уникальный индекс `(sale_id, user_id)` по активным статусам.
**Почему:** при дефиците товара честнее распределять по одной; упрощает модель.
**Альтернатива:** N единиц на покупателя — поле `qty` в брони и лимит в UPDATE.

## ADR-009. Время и деньги
**Решение:** источник времени — `now()` в Postgres; на фронт отдаётся серверное время,
таймер считается по смещению. Деньги — BIGINT в минимальных единицах.

## ADR-010. Фоновые задачи на состоянии БД
**Решение:** asyncio-циклы (свипер броней, сверка платежей, закрытие распродаж, отправка outbox)
выбирают работу запросами к БД, а не из таймеров в памяти; для параллельных воркеров —
`FOR UPDATE SKIP LOCKED`.
**Почему:** переживает перезапуск сервера; простоя ничего не теряет — просроченное обработается при старте.
**Альтернативы:** Celery/APScheduler с брокером — лишняя инфраструктура для этого объёма.

## ADR-011. Тесты — на отдельной базе того же Postgres, пересоздаваемой каждый прогон
**Дата:** 2026-10-09
**Контекст:** CLAUDE.md требует гонять тесты на реальном Postgres, в том числе тесты
конкурентных запросов (несколько соединений, видящих коммиты друг друга). При этом
рабочая база не должна страдать от прогона тестов.
**Решение:** отдельная база на том же контейнере Postgres — `<рабочая>_test`
(или `TEST_DATABASE_URL`). Session-фикстура подключается к служебной базе `postgres`
в режиме AUTOCOMMIT (`CREATE DATABASE` нельзя внутри транзакции), делает
`DROP DATABASE IF EXISTS ... WITH (FORCE)` + `CREATE DATABASE`, подменяет `DATABASE_URL`
в окружении, сбрасывает кэши `get_settings` и engine, после прогона удаляет базу.
**Защита от сноса рабочей базы:** имя тестовой базы обязано заканчиваться на `_test`,
отличаться от базы из `DATABASE_URL` и соответствовать `[A-Za-z0-9_]+` (имя подставляется
в SQL как идентификатор). Иначе — `RuntimeError` до первого запроса к БД.
**Альтернативы:**
- откат транзакции вместо чистой базы — не годится для тестов конкурентности:
  параллельные соединения не видят незакоммиченных данных друг друга;
- схема на тест — не проверяет миграции целиком;
- отдельный контейнер Postgres для тестов — лишний сервис и дольше старт.
**Последствия:** прогон тестов требует прав на `CREATE DATABASE` (у владельца базы они есть);
на шаге миграций в ту же фикстуру добавится `alembic upgrade head`.

## ADR-012. Alembic: async-конфигурация, URL из настроек, явные имена ограничений
**Дата:** 2026-10-09
**Контекст:** весь бэк асинхронный (ADR-001), схема меняется только миграциями,
а тестовая фикстура должна накатывать их внутри уже работающего event loop.
**Решение:**
- `migrations/env.py` работает в двух режимах: обычный создаёт свой `AsyncEngine`,
  а при переданном `config.attributes["connection"]` использует готовое соединение.
  Второй режим нужен тестам: `asyncio.run()` внутри работающего loop вызвать нельзя.
- Адрес БД берётся из настроек приложения (`app.core.config`), в `alembic.ini`
  ключа `sqlalchemy.url` нет вообще — один источник правды и никаких секретов в файлах.
- `compare_type=True` и `compare_server_default=True`: без них autogenerate молча
  пропускает изменения типов и дефолтов.
- Имена ограничений и индексов задаёт `naming_convention` в `MetaData`.
- Тестовая схема создаётся миграциями, а не `Base.metadata.create_all()`.
**Альтернативы:**
- синхронный engine только для миграций — второй драйвер и вторая строка подключения;
- `create_all()` в тестах — быстрее, но тесты проверяли бы схему, которой нет на рабочей базе,
  а частичные индексы и CHECK из миграции остались бы непроверенными;
- `sqlalchemy.url` в `alembic.ini` — дублирование настроек и пароль в файле;
- имена ограничений по умолчанию — `downgrade` ломается, т.к. Postgres генерирует их сам.
**Последствия:** `alembic check` в CI поймает расхождение моделей и миграций;
фикстура и команда `alembic upgrade head` идут одним и тем же кодом env.py.

## ADR-013. Токены: PyJWT, HS256, без состояния на сервере
**Дата:** 2026-10-09
**Контекст:** вход по email без пароля (ADR-007), нужен способ подтверждать,
кто делает запрос. Серверных сессий не хотим — лишнее состояние и ещё одна таблица.
**Решение:** PyJWT, HS256, секрет и срок жизни из настроек. Claims `sub`, `iat`, `exp`;
при проверке `options={"require": ["sub", "exp"]}` — токен без `exp` жил бы вечно.
Передача через `Authorization: Bearer`, зависимость `get_current_user` на `HTTPBearer`
с `auto_error=False` (со включённым автоответом отсутствие заголовка даёт 403, а нужен 401).
`JWT_SECRET` без дефолта в коде: пустой секрет должен ронять старт, а не молча
подписывать токены предсказуемым ключом.
**Альтернативы:** `python-jose` (прежняя рекомендация FastAPI — тяжелее, тянет
`cryptography`, были провалы в поддержке); `authlib` (целый OAuth-фреймворк);
самописный HMAC (нет причин); серверные сессии в БД или Redis (лишнее состояние).
**Последствия:** отозвать отдельный токен нельзя — только сменить секрет. Для
тестового задания приемлемо; при появлении настоящей аутентификации понадобится
список отзыва или короткий срок жизни плюс refresh.

## ADR-014. Статус распродажи и остаток считает Postgres
**Дата:** 2026-10-09
**Контекст:** инвариант 2 — время решает сервер. Статус `upcoming/active/ended`
и остаток нельзя считать по часам Python: остаток обязан быть согласован
со счётчиками на тот же момент, что и проверка времени.
**Решение:** оба значения приходят из SQL — `case` по `now()` и
`quantity - sold - held`. Границы совпадают с условием резерва из `DATA_MODEL.md`
(`now() >= start_at AND now() < end_at AND closed_at IS NULL`): в момент старта
распродажа уже `active`, в момент `end_at` — уже `ended`, заполненный `closed_at`
тоже даёт `ended`. В ответе отдаётся `server_time` — фронт считает таймер
по смещению, не доверяя часам браузера (ADR-009).
**Альтернативы:** считать статус в Python по `datetime.now(UTC)` — часы процесса
и БД расходятся, и UI показывал бы активную кнопку, когда резерв уже отказывает;
считать на фронте — то же, только хуже.
**Последствия:** фронт не вычисляет статус сам, а берёт его из ответа;
проверка границ в тестах задаёт окна выражениями от `now()` в БД.

## ADR-015. Фронт и бэк — два отдельных сервиса, общаются по сети
**Дата:** 2026-10-09
**Контекст:** фронт нужно как-то соединить с API. Обычные варианты — прокси
в dev-сервере Vite, раздача собранной статики из FastAPI или отдельный сервис.
**Решение:** `frontend` — отдельный сервис в compose. Адрес бэкенда приходит
**только** из `VITE_API_URL` (по умолчанию `http://localhost:8000`); прокси Vite
не настраивается, FastAPI статику не раздаёт. Все запросы идут через один модуль
`src/api` — вызовов `fetch` в остальном коде нет.

Важно: `VITE_API_URL` — адрес **хостовой**, не `http://backend:8000`. Запрос делает
браузер, а он имени сервиса compose не разрешает.

**Альтернативы:**
- прокси Vite (`server.proxy`) — в разработке запросы идут на тот же origin,
  CORS не проверяется вообще, и на продакшене он ломается впервые;
- раздача статики из FastAPI — бэкенд начинает отвечать за сборку фронта,
  пропадает hot reload, а деплой фронта и API перестаёт быть независимым.

**Последствия:** CORS обязателен и проверяется с первого дня — `CORS_ORIGINS`
на бэкенде должен содержать адрес фронта. Фронт можно собрать и выложить
куда угодно, указав другой `VITE_API_URL`.

**Токен** хранится в `localStorage`: при хранении только в памяти вход терялся бы
на каждом обновлении страницы. Компромисс — уязвимость к XSS; для тестового
задания принят осознанно, вместе с остальными упрощениями ADR-007.

## ADR-016. Миграции применяются в entrypoint контейнера backend
**Дата:** 2026-10-09
**Контекст:** запуск на чистой машине должен сводиться к `make up` — отдельная команда
`alembic upgrade head` это лишний шаг, о котором легко забыть. При этом сервис никогда
не должен работать на схеме, не соответствующей коду.
**Решение:** `backend/docker-entrypoint.sh` с `set -e` выполняет `alembic upgrade head`
и затем `exec "$@"` (uvicorn). Падение миграции завершает скрипт с ошибкой, до `exec`
дело не доходит — контейнер не стартует. Postgres к этому моменту уже `healthy`
благодаря `depends_on: condition: service_healthy`.
**Альтернативы:**
- отдельный сервис `migrate` с `depends_on: condition: service_completed_successfully` —
  правильнее при нескольких репликах backend, но требование шага было про старт backend;
- `CMD sh -c "alembic upgrade head && uvicorn ..."` — `sh` остаётся PID 1 и хуже
  пробрасывает сигналы остановки;
- оставить ручной шаг — ревьюер получает лишнюю команду и возможность забыть её.
**Последствия:** `docker compose exec` через entrypoint не проходит, поэтому `make test`
и `make seed` миграции не перезапускают. **Ограничение:** при нескольких репликах backend
одновременные `alembic upgrade head` могут конфликтовать — тогда нужно переходить
на отдельный сервис миграций.

## ADR-017. Порт Postgres на хост по умолчанию не публикуется
**Дата:** 2026-10-09
**Контекст:** `POSTGRES_PORT=5432` в шаблоне ломал запуск на любой машине, где уже есть
локальный Postgres или контейнер другого проекта на 5432 — причём на первом же шаге
инструкции. При этом в задокументированном сценарии этот порт не нужен никому:
браузер ходит на 8000, backend внутри сети на `postgres:5432`, тесты идут внутри
контейнера, psql запускается через `docker compose exec postgres psql`.
**Решение:** в `docker-compose.yml` у сервиса `postgres` нет секции `ports`. Кому нужен
внешний psql или GUI-клиент — копирует `docker-compose.override.example.yml`
в `docker-compose.override.yml` (compose подхватывает его автоматически, файл в `.gitignore`).
Порт берётся из `POSTGRES_PORT`, по умолчанию 5433.
**Альтернативы:** оставить 5432 и описать проблему в README (ревьюер всё равно
спотыкается); сменить дефолт на 5433 (менее вероятно занят, но гарантии нет);
`ports: "127.0.0.1::5432"` со случайным портом (адрес пришлось бы каждый раз узнавать).
**Последствия:** `make up` на чистой машине не зависит от того, что занято на 5432.
Доступ к базе с хоста требует одного дополнительного шага, описанного в README.

## ADR-018. Единый порядок захвата блокировок: sales → reservations → orders → payments
**Дата:** 2026-10-10
**Контекст:** тест на конкурентность (шаг 2.3) поймал `deadlock detected`, когда один
покупатель одновременно отменяет бронь и бронирует снова. Резерв и отмена трогали
те же две строки, но в противоположном порядке:

| операция | первый захват | второй захват |
|---|---|---|
| резерв | строка `sales` (`held = held + 1`) | уникальный индекс по `reservations` (`INSERT`) |
| отмена | строка `reservations` (`status = 'cancelled'`) | строка `sales` (`held = held - 1`) |

Лог Postgres:
```
ERROR: deadlock detected
DETAIL: Process 60226 waits for ShareLock on transaction 2284; blocked by process 60220.
        Process 60220 waits for ShareLock on transaction 2283; blocked by process 60226.
        Process 60226: insert into reservations (...)
        Process 60220: update sales set held = held - 1 where id = $1
CONTEXT: while inserting index tuple in relation "uq_reservations_sale_id_user_id_active"
```
Резерв держал `sales` и ждал, пока отмена отпустит строку брони (вставка в частичный
уникальный индекс натыкалась на ещё не закоммиченную `held`-бронь того же покупателя);
отмена держала бронь и ждала `sales`. Через HTTP «отменить и сразу забронировать снова»
давало **HTTP 500 в 5 раундах из 8**: `DBAPIError` не является `IntegrityError`,
поэтому обработчик его не ловил. Данные при этом оставались согласованными —
Postgres откатывает проигравшую транзакцию целиком, — то есть это отказ
в обслуживании, а не оверсейл.

**Решение:** зафиксировать единый порядок захвата для всех операций —
`sales` → `reservations` → `orders` → `payments` (инвариант 10 в CLAUDE.md).
Отмена приведена к нему: `sale_id` брони читается обычным `SELECT` без блокировки
(поле неизменяемое, это безопасно), затем `SELECT ... FROM sales ... FOR UPDATE`,
и только потом тот же условный `UPDATE reservations ... WHERE status = 'held'`.
Решение «можно ли отменять» по-прежнему принимает условный UPDATE — захват строки
`sales` лишь выстраивает порядок и ничего не решает.

**Альтернативы:**
- **ретрай при `SQLSTATE 40P01`** — лечит симптом, инверсия порядка остаётся
  и всплывёт снова на оплате и свипере, где таблиц станет четыре. Ретраи ещё
  и маскируют проблему: в логах видно только замедление;
- **отдавать 409 `retry_later`** — честно, но перекладывает ретрай на клиента
  в совершенно штатном сценарии «передумал и беру снова»;
- **отложенный уникальный индекс** — невозможно: частичные уникальные индексы
  в Postgres нельзя объявить `DEFERRABLE`;
- **одна общая блокировка на распродажу** (advisory lock) — сериализует вообще всё,
  включая независимые операции разных покупателей.

**Последствия:** отмена делает на один запрос больше (`SELECT` + `FOR UPDATE`).
Взамен — ни одного дедлока: тест №3 прошёл 20 раз подряд, HTTP-прогон из 30 раундов
дал 0 пятисоток (было 5 из 8). Порядок обязателен для свипера и оплаты: там
добавятся `orders` и `payments`, и любая операция, берущая несколько таблиц,
должна идти по цепочке слева направо.

# CLAUDE.md — Flash Sale

Тестовое задание: сервис флэш-распродаж. Магазин выставляет партию товара по спеццене
на короткое время, покупателей больше, чем товара.

## Стек
- backend/ — Python 3.12, FastAPI, SQLAlchemy 2 (async, asyncpg), Alembic, pydantic-settings, uv
- frontend/ — React + Vite + TypeScript
- payment-stub/ — отдельный FastAPI-сервис, эмулирует платёжку (approve / decline / hang)
- PostgreSQL 16, Mailpit (SMTP + веб-UI для писем)
- Всё поднимается через `docker compose up`

## Команды
- Запуск всего: `docker compose up --build`
- Миграции: `docker compose exec backend alembic upgrade head`
- Новая миграция: `docker compose exec backend alembic revision --autogenerate -m "<msg>"`
- Тесты бэка: `docker compose exec backend pytest -q`
- Seed: `docker compose exec backend python -m app.scripts.seed`
- Письма: http://localhost:8025 · Swagger: http://localhost:8000/docs · Фронт: http://localhost:5173

## Инварианты (нарушать нельзя)
1. Продано + удержано никогда не больше quantity. Резерв — только атомарным условным UPDATE
   в БД. Никаких «прочитали остаток → проверили в Python → записали».
2. Время решает сервер (`now()` в БД). Проверка старта/окончания всегда на бэке, фронт только показывает.
3. Бронь `held` живёт 10 минут. Свипер снимает только `held` с истёкшим `expires_at`.
4. Бронь в `paying` не истекает: начатая оплата доводится до конца, даже если заглушка ответила позже.
5. Один заказ и один платёж на бронь (уникальные индексы + Idempotency-Key). Двойной клик ничего не дублирует.
6. Каждое письмо отправляется ровно один раз: пишется в `outbox` с уникальным `dedup_key`
   в той же транзакции, что и смена статуса.
7. Все изменения остатков рассылаются клиентам через WebSocket (Postgres LISTEN/NOTIFY).
8. Деньги — целые числа в минимальных единицах (`*_minor`, BIGINT). Никаких float.
9. Время в БД — только `timestamptz` (UTC).
10. Порядок захвата блокировок во всех операциях один: `sales` → `reservations` →
    `orders` → `payments`. Операция, которой нужны несколько из этих таблиц, берёт их
    строго в этом порядке — иначе встречные операции дают дедлок (ADR-018: отмена
    захватывала бронь раньше распродажи, и одновременная отмена с резервом падала
    с `deadlock detected`). Свипер, оплата и любые будущие операции обязаны соблюдать
    этот порядок; если нужная строка `sales` известна не сразу, её id читается
    обычным `SELECT` (он неизменяем), а затем берётся `SELECT ... FOR UPDATE`.

Модель данных: `docs/DATA_MODEL.md`. Принятые решения: `docs/DECISIONS.md`.

## Как работать
- Перед крупной задачей предложи план и дождись подтверждения. Ничего не меняй до «ок».
- Любое изменение логики резерва, оплаты, свипера или писем начинается с теста, который
  воспроизводит сценарий (включая конкурентные запросы). Тесты гоняются на реальном Postgres.
- Схему БД меняем только новыми миграциями Alembic. Существующие миграции не редактируем.
- После каждого завершённого шага:
  1. добавь запись в `docs/DEVLOG.md`; время бери командой `date '+%Y-%m-%d %H:%M %Z'`, не выдумывай;
  2. если принято решение с альтернативами — добавь запись в `docs/DECISIONS.md`;
  3. предложи сообщение коммита (Conventional Commits: feat/fix/test/docs/chore/refactor).
- Не добавляй зависимости без объяснения, зачем они нужны и чем плохи альтернативы.
- Не отключай и не ослабляй тесты, чтобы они прошли. Если тест падает — разберись в причине.
- Не храни секреты в коде; всё через `.env` (в репозитории только `.env.example`).
- Если требование задания неоднозначно — спроси, а не додумывай молча.

## Стиль кода
- Backend: типизация везде, ruff (lint + format). Слои: `api/` (роутеры) → `services/` (бизнес-логика,
  транзакции) → `models/` (SQLAlchemy). SQL для критичных операций — явный и читаемый.
- Frontend: функциональные компоненты, хуки, API-клиент в одном модуле `src/api/`.
- Имена в коде и коммитах — на английском, документация — на русском.

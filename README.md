# Flash Sale

[![CI](https://github.com/arsenzhanykulov/flash-sale/actions/workflows/ci.yml/badge.svg)](https://github.com/arsenzhanykulov/flash-sale/actions/workflows/ci.yml)

Сервис флэш-распродаж: магазин выставляет партию товара по спеццене на короткое
время, покупателей больше, чем товара. Главное требование — ни одна единица
не может быть продана дважды, даже когда десятки покупателей жмут «Купить»
в одну секунду. Это [доказано тестами и нагрузочным прогоном](#как-доказана-корректность),
а не обещано.

Запуск — три команды, нужен только Docker: [«Запуск с чистой машины»](#запуск-с-чистой-машины).
Подробности по API и поведению — [docs/GUIDE.md](docs/GUIDE.md).

## Запуск с чистой машины

Нужен **только Docker** — Python, Node, Postgres и почтовый сервер живут
в контейнерах и на хост ничего не ставят.

- **Docker Engine 24+** (или Docker Desktop 4.x)
- **Docker Compose v2.20+** — нужны ключ `name:` и флаг `--wait`

Проверялось на Docker 25.0.2 и Compose v2.24.3 (macOS). `make` не обязателен:
рядом с каждой целью указана исходная команда.

```bash
git clone https://github.com/arsenzhanykulov/flash-sale.git
cd flash-sale
cp .env.example .env      # без этого шага compose скажет "env file ... not found"
make up                   # docker compose up --build -d --wait
make seed                 # docker compose exec backend python -m app.scripts.seed
```

Первая сборка занимает несколько минут. `make up` возвращает управление только
после healthcheck-ов, поэтому `make seed` можно запускать сразу следом.
Миграции накатываются автоматически при старте контейнера `backend`; если
миграция упадёт, контейнер не поднимется — на старой схеме сервис работать
не будет ([ADR-016](docs/DECISIONS.md)).

Остановить — `make down` (`docker compose down`), данные останутся в томе
`pgdata`. Полный сброс вместе с базой — `docker compose down -v`.

Нужны свободные порты **8000**, **5173**, **1025**, **8025** и **8100**. Порт
Postgres на хост не публикуется, поэтому локальный Postgres на 5432 не мешает
([ADR-017](docs/DECISIONS.md)). Что делать, если порт занят, —
[в руководстве](docs/GUIDE.md#если-порт-занят).

### Вход

Пароля нет ([ADR-007](docs/DECISIONS.md)): на экране входа достаточно email.
`make seed` создаёт четырёх пользователей.

| Email | Роль | Что видно |
|---|---|---|
| `shop@example.com` | магазин | `/shop` — своя распродажа, выручка |
| `shop2@example.com` | магазин | `/shop` — своя, чужой не видит |
| `buyer1@example.com`, `buyer2@example.com` | покупатели | витрина, корзина, заказы |

Любой другой email тоже подойдёт — неизвестный становится покупателем. Роль
«магазин» входом получить нельзя, только через seed или SQL (на это есть тест).

Два магазина в seed нужны ровно для одной проверки: на дашборде каждый видит
только свои распродажи, а не все в системе.

### Посмотреть главное за пять минут

```bash
make race    # два покупателя за одну единицу: 201 и 409 sold_out
make load    # 200 покупателей на 10 единиц: продано ровно 10
make test    # 166 тестов бэкенда + 24 заглушки
```

Платёжные сценарии переключаются на страничке заглушки (http://localhost:8100):
`approve` — оплата проходит, `decline` — единица возвращается на витрину,
`hang` — платёж висит, пока его не отпустят вручную, и заказ всё равно
досчитывается.

## Что работает

- **Резерв без оверсейла.** Одна единица — один атомарный условный `UPDATE`;
  остаток не вычитывается в Python. Последняя линия защиты в схеме:
  `CHECK (sold + held <= quantity)`.
- **Отмена брони** — идемпотентная, возвращает единицу; повторный клик безвреден.
- **Свипер** истёкших броней: единица возвращается не позже чем через
  `RESERVATION_TTL_SECONDS + SWEEPER_INTERVAL_SECONDS`. Брони в `paying`
  не истекают — начатая оплата доводится до конца.
- **Оплата** через отдельный сервис-заглушку: заказ и платёж по ключу
  идемпотентности, вызов провайдера вне транзакции (сеть не держит блокировки),
  результат вебхуком с проверкой подписи по сырому телу.
- **Сверка зависших платежей**: потерянный вебхук не оставляет заказ
  недосчитанным — backend сам доспрашивает провайдера, потолок
  `RECONCILE_BACKOFF_MAX_SECONDS` (300 с по умолчанию).
- **Письма** через transactional outbox: запись ровно одна на событие
  (уникальный `dedup_key` в той же транзакции, что смена статуса), доставка
  at-least-once с постоянным `Message-ID` — граница гарантии
  описана честно в [ADR-024](docs/DECISIONS.md).
- **Закрытие распродажи по времени**: `held` снимаются, владельцам уходит письмо,
  `quantity` не меняется — магазину нужна цифра «не продано».
- **Живые остатки** по WebSocket через триггер в БД: новая операция не может
  забыть уведомление, потому что его отправляет не код сервиса.
- **Витрина и корзина**: таймеры по серверному времени, корзина переживает
  перезагрузку, итог оплаты виден без перезагрузки, вкладки одного покупателя
  синхронизируются через `BroadcastChannel` — без дополнительной нагрузки на бэк.
- **Кабинет покупателя** `/orders` и **дашборд магазина** `/shop` с живыми
  счётчиками по одному WebSocket-соединению на все распродажи.
- **166 тестов бэкенда и 24 теста заглушки** на реальном Postgres, включая
  гонки, дедлоки, конкурентные отмены и доставку письма в настоящий Mailpit.
- **CI** на каждый PR: тесты, линт, типы, сборка.

## Чего нет и что не делали

Честно, без преувеличений.

**Не реализовано:**

- **Создание распродажи магазином.** Ни API, ни экрана: распродажи появляются
  через `make seed` или SQL. Дашборд только показывает. Это заметный пробел
  в сценарии «магазин выставляет товар», и закрывался бы он первым.
- **Тестов фронтенда нет вообще** — ни unit, ни e2e. Проверка фронта только
  ручная по чек-листам из PR плюс `tsc` и oxlint. Для теста по корректности
  резерва приоритет был у бэкенда, но дыра есть, и она настоящая.
- **Настоящая аутентификация.** Вход по одному email без пароля —
  осознанное упрощение ([ADR-007](docs/DECISIONS.md)), чтобы не тратить время
  на то, что в задании не проверяется. В прод так нельзя.
- **Нет ограничения частоты запросов** (rate limiting) и защиты от перебора.
- **Нет прод-конфигурации**: dev-секреты в `.env.example`, `uvicorn --reload`
  в CMD, HTTPS и обратного прокси нет, масштабирование не настраивалось.
- **GIF с гонкой не записан** — в README осталась закомментированная ссылка;
  папки `docs/media/` в репозитории нет. Вместо видео — `make race`
  и `make load`, которые показывают то же живьём.

**Сознательные ограничения, зафиксированные в ADR:**

- **Доставка письма — at-least-once, а не exactly-once.** Между «SMTP принял»
  и «отметили отправленным» нет общей транзакции; выбран дубль, а не потеря,
  и повтор подавляется постоянным `Message-ID` ([ADR-024](docs/DECISIONS.md)).
- **Распродажа, созданная при открытом дашборде**, в живую подписку не попадёт:
  список формируется при загрузке. Закрыто перезапросом при возврате на вкладку
  ([ADR-026](docs/DECISIONS.md)).
- **Нагрузочный прогон — по одной распродаже**, без перцентилей: он доказывает
  отсутствие оверсейла, а не производительность.
- **Нагрузочный прогон не в CI**: ему нужны все поднятые сервисы вместе
  с заглушкой.
- **Пул соединений 10 + 20** — предел пропускной способности одного процесса
  backend. На корректность не влияет: лишние запросы ждут соединение.

**Проверено не мной:** браузерные сценарии. Браузерные инструменты в сессиях
агента были недоступны, поэтому фронт проверялся скриптами на контракт API
плюс чек-листами в описаниях PR, которые проходил автор руками. В DEVLOG это
отмечено отдельной строкой на каждом шаге фронта.

## Как доказана корректность

Главное требование — не продать одну единицу дважды. Ниже короткая версия;
полные цифры, вывод прогонов и разбор находок — в [docs/DEVLOG.md](docs/DEVLOG.md)
и [docs/GUIDE.md](docs/GUIDE.md).

### Увидеть гонку одной командой

```bash
make race    # docker compose exec backend python -m app.scripts.race
```

Два покупателя жмут «Купить» одновременно (`asyncio.gather`, а не подряд)
по распродаже с одной единицей:

```
  buyer1@example.com       201  бронь ede66867-...
  buyer2@example.com       409  sold_out

остаток после гонки: 0
```

### 200 покупателей на 10 единиц

```bash
make load    # docker compose exec backend python -m app.scripts.load
```

Скрипт создаёт свою распродажу и считает только по ней; покупательский путь
идёт по HTTP в запущенный backend, то есть в прогон попадают пул соединений,
вебхук заглушки и запись письма. Настоящий вывод:

```
  продано .............. 10 из 10
  в корзинах (held) .... 0
  оверсейл ............. нет (10 + 0 ≤ 10)
  заказы по статусам ... {'paid': 10}
  писем в outbox ....... 10
      order_paid / sent: 10
  отказы по кодам:
      409 sold_out                 190
  время прогона ........ 5.41 с
```

**10 + 190 = 200**: каждый покупатель получил честный ответ — либо бронь, либо
`409 sold_out`, ни одной ошибки сервера. Писем ровно столько же, сколько продаж.
При оверсейле, оставшихся `held` или расхождении писем скрипт выходит
с ненулевым кодом; проверено и в обратную сторону — с остановленной заглушкой
прогон честно падает.

### Два случая, где корректность ломалась

Оба нашёл тест, а не прод.

**1. Оверсейл.** Резерв сначала был написан наивно **намеренно** (прочитать
остаток, решить в Python, записать), затем появился красный тест, и только
потом исправление.

| 10 покупателей на 1 единицу | наивная версия | атомарный `UPDATE` |
|---|---|---|
| выдано броней | **10** | **1** |
| реально активных броней | **10** | **1** |

Неочевидное: `CHECK (sold + held <= quantity)` при этом **не срабатывал** —
наивный код писал посчитанное значение, и проверка `0 + 1 <= 1` честно
проходила дважды. Последняя линия защиты работает только в паре с инкрементом;
это проверено намеренной поломкой рабочего запроса. Разбор —
[ADR-002](docs/DECISIONS.md).

**2. Дедлок.** Конкурентный тест поймал `deadlock detected`: резерв и отмена
брали те же две строки в противоположном порядке.

| | до | после |
|---|---|---|
| HTTP «отменить и сразу забронировать снова» | **500 в 5 раундах из 8** | **0 из 30** |
| тест, 20 прогонов подряд | падал | 0 провалов |

Данные не портились — Postgres откатывает проигравшую транзакцию, то есть это
был отказ в обслуживании, а не оверсейл. Закрыто **единым порядком захвата
блокировок** `sales → reservations → orders → payments` (инвариант 10
в [CLAUDE.md](CLAUDE.md)), а не ретраем на `SQLSTATE 40P01`: ретрай лечил бы
симптом, а инверсия вернулась бы на оплате ([ADR-018](docs/DECISIONS.md)).

### Как устроены сами тесты

Конкурентные тесты не «надеются» на параллельность, а доказывают её: барьер
снимается **после** того, как каждый участник захватил соединение, и тест
проверяет, что все `pg_backend_pid` различны. Число участников выбрано под пул
SQLAlchemy, а не под `max_connections` Postgres — иначе лишние встали бы
в очередь на пуле, запросы пошли бы последовательно и тест прошёл бы
по неверной причине.

Тесты идут на **реальном Postgres** в отдельной базе, которая пересоздаётся
каждый прогон; схема накатывается миграциями, а не `create_all`
([ADR-011](docs/DECISIONS.md), [ADR-012](docs/DECISIONS.md)). Величины
проверяются по своему объекту, а не по всей таблице: иначе соседний тест,
добавивший данные, ломает проверку — так уже трижды падали тесты свипера,
писем и дашборда.

## Шаблоны и генераторы

- **frontend** — официальный шаблон Vite (`react-ts`): от него остались
  `vite.config.ts`, тройка `tsconfig*.json`, `.gitignore` и **oxlint**
  (современный шаблон Vite идёт с ним вместо ESLint — взят дефолт шаблона,
  это одна зависимость вместо пяти). Точная команда генерации в журнале
  не зафиксирована.
- **backend** — проект `uv` со своим `pyproject.toml`; `uv.lock` сгенерирован
  одноразовым `docker run` с официальным образом `uv`, чтобы ничего не ставить
  на хост. Структура слоёв (`api/` → `services/` → `models/`) написана руками.
- **Alembic** — конфигурация написана под async вручную
  ([ADR-012](docs/DECISIONS.md)): `env.py` поддерживает два режима, URL берётся
  из настроек, а не из `alembic.ini`. Сами миграции создаются
  через `alembic revision --autogenerate` и затем сверяются построчно
  с [DATA_MODEL.md](docs/DATA_MODEL.md) и переписываются в читаемый вид.
- **Образы** — официальные: `postgres:16`, `axllent/mailpit`,
  `ghcr.io/astral-sh/uv:python3.12-bookworm-slim`, `node:24-alpine`.
- **UI-библиотек и генераторов интерфейса нет**: вся вёрстка и CSS написаны
  руками, зависимости фронта — только `react`, `react-dom`, `react-router-dom`.
- Код писался агентом (Claude Code) под ревью автора — это основной «генератор»
  в этом проекте, см. [«Чем делали»](#чем-делали).

## Что сделали бы следующим заходом

Собрано из DEVLOG и ADR, по убыванию важности:

1. **Создание и редактирование распродажи магазином** — API и экран. Сейчас
   это единственный сценарий из задания, закрытый только seed-ом.
2. **Тесты фронтенда**: unit на хуки корзины и дашборда, e2e на сценарий
   «двойной клик по Оплатить» и «распродажа закрылась с корзиной в held».
   Сейчас фронт держится на ручных чек-листах.
3. **Событие «у магазина появилась распродажа»** — подписка по `shop_id`
   вместо списка id, чтобы дашборд подхватывал новые распродажи без
   перезапроса ([ADR-026](docs/DECISIONS.md)).
4. **Нагрузочный прогон по нескольким распродажам** с перцентилями задержек
   и опцией держать `held` без оплаты — проверить свипер под нагрузкой.
5. **Вынести пул и лимиты в прод-профиль**, добавить несколько воркеров
   uvicorn и проверить, что фоновые циклы (свипер, сверка, outbox, закрытие)
   корректно делятся между процессами. Сейчас всё в одном процессе, и хотя
   конкурентность каждого цикла проверена тестами (10 экземпляров свипера
   одновременно), многопроцессный запуск не прогонялся.
6. **Метрики и алерты**: писем в `failed`, платежей в `pending` дольше
   потолка сверки, глубина очереди outbox. Сейчас это видно только в логах
   и в БД.
7. **Настоящая аутентификация** с паролем или magic-link, роли через claims,
   ограничение частоты запросов на вход и резерв.
8. **GIF или короткое видео** гонки за последнюю единицу в README — сейчас
   вместо него две команды.
